问题序号：1：流式消息骨架呈现与打字机异常问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：中
- **影响范围**：AI 聊天（教材/通用等）消息显示
- **发现日期**：2025-12-11
- **解决状态**：已解决

## 问题现象
AI 绘图/文本混合场景中，用户发送纯文本时也会长时间显示“绘图中”骨架屏；即使进入 talking 阶段，AI 回复仍以打字机效果缓慢渲染，无法做到“收到多少展示多少”。

## 复现步骤
1. 在 AI Textbook 场景中发送纯文本问题。
2. 后端返回 `agent_status: "drawing"` 的空帧后立即返回携带文本的 `talking` 帧。
3. 前端仍持续显示骨架屏，文本只会在打字机逐字播放完后才出现。

## 用户体验
- 用户无法确认 AI 是否已开始回复，误以为仍在“绘图中”。
- 文本延迟渲染导致交互节奏被打断。
- 骨架/打字机的组合与真实状态不符，用户感知混乱。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/chat/ChatMessage.vue`：StreamingMessage 的 typewriter 入口。
  - `imates-web/src/components/chat/StreamingMessage.vue`：骨架/打字机渲染逻辑。
  - `imates-web/src/stores/aiTextbookChatStore.ts`、`imates-web/src/stores/aiGeneralChatStore.ts`：onStream 回调处理。
- **涉及模块**：
  - Chat 视图渲染模块。
  - AI 文本/截图聊天 store。

## 技术原因 (❌)
1. `createTempAiReplyMessage` 默认 `isStreaming: true`，即使未收到任何帧也会直接触发骨架。
2. `aiTextbookChatStore.onStream` 仅切换 `isStreaming`，完全忽略文本 chunk，导致内容直到 onComplete 才一次性写入。
3. `StreamingMessage` 始终启用打字机效果，即便需求是“talking 帧立刻展示”。

```ts
// ❌ 旧 onStream 逻辑（节选）
(chunk: string, isComplete: boolean) => {
  if (isComplete) {
    updateMessage(tempReplyId, { isStreaming: false })
  } else {
    updateMessage(tempReplyId, { isStreaming: true })
  }
}
```

## 正确实现方案 (✅)
1. 临时 AI 消息默认 `isStreaming=false`，只在真正收到帧时开启骨架。
2. `onStream` 中区分 `chunk === ''`（drawing 控制帧）与真实文本；空 chunk 只更新 `isStreaming`，非空 chunk 立即累积到 `content`。
3. `StreamingMessage` 关闭打字机模式，直接渲染传入的内容。

```ts
// ✅ 新 onStream 逻辑
let accumulatedContent = ''
(chunk: string, isComplete: boolean) => {
  if (isComplete) {
    updateMessage(tempReplyId, { isStreaming: false })
    return
  }
  if (!chunk) {
    updateMessage(tempReplyId, { isStreaming: true })
    return
  }
  accumulatedContent += chunk
  updateMessage(tempReplyId, { content: accumulatedContent, isStreaming: true })
}
```

```vue
<!-- ✅ StreamingMessage 强制关闭打字机 -->
<StreamingMessage
  :content="message.content"
  :is-streaming="message.isStreaming"
  :enable-typewriter="false"
/>
```

## 测试验证
- **测试场景**：
  - 场景1：发送触发 `drawing→talking` 的截图问题，观察骨架→文本切换；预期骨架只在空内容帧显示，talking 帧立即渲染内容。
  - 场景2：发送纯文本（无 drawing）的问题；预期不会出现骨架，内容实时呈现。
- **验证方法**：
  - 方法1：浏览器 DevTools 观察消息对象 `isStreaming`、`content` 的变化。
  - 方法2：抓取 SSE 日志，确认每个 chunk 及时写入。

## 预防措施
- 在 store 中统一封装 SSE chunk 处理，避免遗漏 content 累积。
- 为 StreamingMessage 添加单元测试/Storybook 场景验证不同状态。
- 将骨架显示与 `content` 关联，杜绝“无内容也显示打字机”情况。

## 可复用经验
- SSE 流式渲染应确保控制帧与内容帧分离处理。
- UI 骨架与文本展示条件要基于数据状态，而非“是否在请求中”。
- 打字机效果需与业务需求一致，默认关闭可以避免延迟体验。
