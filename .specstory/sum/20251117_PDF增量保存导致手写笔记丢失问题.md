问题序号：PDF 增量保存导致手写笔记丢失问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：中
- **影响范围**：PDF 浏览器中的手写高亮/画笔笔记持久化功能
- **发现日期**：2025-11-17
- **解决状态**：已解决

## 问题现象
在 `PdfPage.vue` 中使用手写高亮/画笔在 PDF 上绘制后，当前会话中可以看到笔迹，但退出 PDF 再重新进入同一教材文件时，之前的手写笔记全部丢失，看起来像是没有保存。

控制台报错如下：

```text
PdfPage.vue:379 保存 PDF 到 IndexedDB 失败 Error: Can't do incremental writes on a repaired file
    at saveCurrentPdfToStorage (PdfPage.vue:361:24)
    at Proxy.handleHighlightPointerUp (PdfPage.vue:740:10)
```

## 复现步骤
1. 打开教材 PDF（通过 `PdfViewerView`，路由参数中带有 `resourceId` 和 `id`）。
2. 在工具栏中选择高亮/画笔工具，在 PDF 页面上手写绘制几笔。
3. 松开手写笔/鼠标，当前会话中可以看到高亮或画笔效果。
4. 退出当前 PDF 页面（例如路由返回或关闭后重新进入同一 PDF）。
5. 重新打开同一教材 PDF，发现刚刚手写的高亮/画笔痕迹全部消失。

## 用户体验
- 影响点1：用户认为手写批注已经保存，但重新进入后发现所有笔记丢失，造成强烈的不信任感。
- 影响点2：需要重新绘制高亮/笔记，增加重复劳动，学习体验变差。
- 影响点3：错误只在控制台出现，不熟悉开发工具的用户难以及时发现问题原因。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：负责 PDF 渲染、手写高亮/画笔/橡皮擦逻辑，以及将带注释的 PDF 保存回 IndexedDB。
  - `imates-web/src/views/PdfViewerView.vue`：负责根据路由参数从 IndexedDB 读取 PDF 二进制数据，并以 `File` 形式传入 `PdfPage` 加载。
- **涉及模块**：
  - MuPDF 文档操作模块：`mupdf.Document`、`pdf.saveToBuffer`、`page.createAnnotation('Ink')` 等。
  - 本地资源管理模块：`resourceManager.updateFileData`、`resourceManager.getFileData`。

## 技术原因 (❌)
1. 原因1：`saveCurrentPdfToStorage` 中强制使用增量保存 `pdf.saveToBuffer('incremental')`，但对于 MuPDF 判定为 "repaired file" 的 PDF，该 API 直接抛出异常 `Can't do incremental writes on a repaired file`。
2. 原因2：异常被抛出后没有回退逻辑，导致整个保存流程中断，后续不会调用 `resourceManager.updateFileData` 写回 IndexedDB。
3. 原因3：渲染逻辑是基于当前运行时内存中的 `pdfDoc` 来重绘当前页，当前会话中能看到新绘制的 Ink 注释，但退出组件后重新打开时，实际上重新从 IndexedDB 读取的是“旧的未保存版本”PDF，因此看起来像“笔记丢失”。

错误代码示例（节选自修改前的 `PdfPage.vue`）：

```typescript
// 将当前 PDF 文档（包含所有批注）保存回 IndexedDB 中的教材文件条目
const saveCurrentPdfToStorage = async () => {
  if (!pdfDoc.value) return

  const pdf = pdfDoc.value.asPDF()
  if (!pdf) return

  try {
    // 使用 MuPDF 提供的增量保存，将当前文档导出为缓冲区
    const buffer = pdf.saveToBuffer('incremental') as any
    const uint8 = buffer.asUint8Array() as Uint8Array

    // 复制到新的 Uint8Array，避免 SharedArrayBuffer 类型问题
    const data = new Uint8Array(uint8.length)
    data.set(uint8)

    // 从路由参数中获取当前文件的 resourceId
    const resourceId = route.query.resourceId as string | undefined
    if (!resourceId) {
      console.warn('saveCurrentPdfToStorage: 缺少 resourceId，无法保存 PDF')
      return
    }

    // 仅更新 textbook_files 表中的二进制数据
    await resourceManager.updateFileData(resourceId, data)
    console.log('PDF 已保存到 IndexedDB', { resourceId, size: data.byteLength })
  } catch (e) {
    console.error('保存 PDF 到 IndexedDB 失败', e)
  }
}
```

## 正确实现方案 (✅)
1. 方案1：在 `saveCurrentPdfToStorage` 中对 `saveToBuffer('incremental')` 增加异常捕获，当出现 `Can't do incremental writes on a repaired file` 或其他错误时，自动回退到完整保存 `saveToBuffer()`（或 `saveToBuffer('full')`）。
2. 方案2：保持后续复制到 `Uint8Array` 与 `resourceManager.updateFileData` 的逻辑不变，确保无论增量还是完整保存，最终都会把最新 PDF 写回 IndexedDB。
3. 方案3：通过控制台日志或 UI 提示区分“增量保存成功”和“回退到完整保存”的情况，方便后续调试和监控。

修复后的关键代码示例（节选自 `PdfPage.vue`）：

```typescript
// 将当前 PDF 文档（包含所有批注）保存回 IndexedDB 中的教材文件条目
const saveCurrentPdfToStorage = async () => {
  if (!pdfDoc.value) return

  const pdf = pdfDoc.value.asPDF()
  if (!pdf) return

  try {
    // 使用 MuPDF 提供的增量保存，将当前文档导出为缓冲区
    let buffer: any
    try {
      buffer = pdf.saveToBuffer('incremental')
    } catch (e) {

      buffer = pdf.saveToBuffer() // 或 'full'
    }
    const uint8 = buffer.asUint8Array() as Uint8Array

    // 复制到新的 Uint8Array，避免 SharedArrayBuffer 类型问题
    const data = new Uint8Array(uint8.length)
    data.set(uint8)

    // 从路由参数中获取当前文件的 resourceId
    const resourceId = route.query.resourceId as string | undefined
    if (!resourceId) {
      console.warn('saveCurrentPdfToStorage: 缺少 resourceId，无法保存 PDF')
      return
    }

    // 仅更新 textbook_files 表中的二进制数据
    await resourceManager.updateFileData(resourceId, data)
    console.log('PDF 已保存到 IndexedDB', { resourceId, size: data.byteLength })
  } catch (e) {
    console.error('保存 PDF 到 IndexedDB 失败', e)
  }
}
```

## 测试验证
- **测试场景**：
  - 场景1：在“正常 PDF 文件”上手写高亮/画笔，检查退出重进后笔迹是否保留。
  - 场景2：在被 MuPDF 认定为 "repaired file" 的 PDF 上手写，确保控制台打印“incremental 保存失败，回退到 full 保存”日志，同时退出重进后笔迹仍然存在。
- **验证方法**：
  - 方法1：观察 IndexedDB 中 `textbook_files` 对应记录的大小和更新时间，确认 PDF 实际被更新。
  - 方法2：多次进出同一 PDF 页面，验证所有新绘制的高亮/画笔都能稳定复现，且在刷新浏览器后依然存在。

## 预防措施
- 措施1：对所有依赖第三方库的“优化型”调用（如增量保存、差量同步）增加回退策略，以避免在特定边界条件下整个流程失败。
- 措施2：在保存失败时增加及时的开发日志或用户提示，而不是静默失败，便于快速定位问题。
- 措施3：在引入新保存策略（如增量保存）时，配套添加针对异常场景（repaired file、只读文件等）的测试用例。

## 可复用经验
- 经验1：对于“增量更新”这类优化措施，必须保留“完整更新”的兜底路径，以保证功能在所有输入条件下可用。
- 经验2：保存类操作一旦失败，必须有明确的日志或错误提示，否则问题会以“数据丢失”的形式暴露给最终用户。
- 经验3：前端与本地存储（如 IndexedDB）交互时，要注意二进制数据类型转换（例如避免直接持有 `SharedArrayBuffer`），应统一转换为 `Uint8Array` 等安全类型后再写库。
