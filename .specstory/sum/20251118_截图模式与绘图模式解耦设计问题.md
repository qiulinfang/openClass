问题序号：截图模式与绘图模式解耦设计问题

## 问题元信息
- **问题分类**：前端/架构
- **严重程度**：中
- **影响范围**：PDF 查看页的截图、高亮、画笔、橡皮擦工具交互
- **发现日期**：2025-11-18
- **解决状态**：已解决

## 问题现象
在早期实现中：
- `currentMode` 同时承载了“手势/绘图/截图”等多种模式，包括 `'hand' | 'note' | 'highlighter' | 'pen' | 'eraser-draw' | 'screenshot'`；
- 截图逻辑与高亮、画笔复用一套 pointer 事件，并通过 `currentMode === 'screenshot'` 进行分支；
- 在切换工具（例如从截图切回手势或笔记）时，截图状态（如 `screenshotRect`、`isDraggingScreenshot`）没有统一入口清理，增加了行为不一致的风险；
- 多指缩放、截图、绘图之间的状态边界不清晰，维护成本高。

## 复现步骤
1. 打开 PDF 查看页面并加载 PDF。
2. 在工具栏中多次切换工具：手势 → 高亮 → 截图 → 笔记 → 截图。
3. 观察：
   - 截图、绘图逻辑都在 `handleHighlightPointerDown/Move/Up` 中做分支判断；
   - 切换流程复杂时，容易出现状态难以追踪的问题（如截图框残留、绘图与截图之间的竞争）。

## 用户体验
- 影响点1：开发和维护人员难以快速理解“当前模式”含义，增加修改和扩展工具条的风险。
- 影响点2：当后续新增更多交互（如局部放大、矩形选择）时，继续向 `currentMode` 添加枚举值会进一步放大复杂度。
- 影响点3：工具切换时的联动（关闭笔记面板、退出截图模式等）散落在各处，问题排查困难。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：定义 `currentMode` 与截图、绘图、手势的交互逻辑。
  - `imates-web/src/views/PdfViewerView.vue`：通过 `pdfPageRef` 调用 `toggleHighlightMode`、`togglePenMode`、`toggleScreenshotMode` 等方法。
- **涉及模块**：
  - 统一工具栏（`UnifiedToolbar`）与 `usePdfViewerStore` 中 `selectedTool`、`drawingConfig` 的联动。
  - 截图与笔记模块（右侧笔记面板、内联笔记锚点）。

## 技术原因 (❌)
1. 原因1：将截图也纳入 `PdfInteractionMode` 枚举，导致 `currentMode` 同时承担“工具选择”和“截图状态”两种职责，不符合单一职责原则。
2. 原因2：截图逻辑深入绑定在高亮/画笔的 pointer 事件中 (`handleHighlightPointerDown/Move/Up`)，通过 `currentMode === 'screenshot'` 进行分支，使得代码耦合度高。
3. 原因3：没有为截图和笔记模式提供统一的“进入/退出”管理函数，导致面板开启/关闭、状态重置逻辑散落在多个函数中。

❌ 错误/耦合度高的实现示例：
```ts
// 旧的交互模式定义
 type PdfInteractionMode =
   | 'hand'
   | 'note'
   | 'highlighter'
   | 'pen'
   | 'eraser-draw'
   | 'screenshot'

 const currentMode = ref<PdfInteractionMode>('hand')

// pointerdown 中根据 currentMode 混合处理截图和绘图
const handleHighlightPointerDown = (
  event: PointerEvent,
  pageIndex: number,
  layout: { width: number; height: number },
) => {
  // 截图逻辑
  if (currentMode.value === 'screenshot') {
    // ... 截图起点逻辑
    screenshotRect.value = { pageIndex, x1: x, y1: y, x2: x, y2: y }
    isDraggingScreenshot.value = true
    return
  }

  // 绘图逻辑
  if (!['highlighter', 'pen', 'eraser-draw'].includes(currentMode.value)) return
  // ... 高亮、画笔、橡皮逻辑
}
```

## 正确实现方案 (✅)
1. 方案1：将截图从 `PdfInteractionMode` 中移除，仅保留 `'hand' | 'note' | 'highlighter' | 'pen' | 'eraser-draw'`；新增独立的 `isScreenshotMode` 状态用于控制截图模式。
2. 方案2：提供 `enterScreenshotMode` 与 `exitScreenshotMode` 两个明确的入口，统一负责重置截图状态、关闭/打开笔记面板、恢复到合适的 `currentMode`。
3. 方案3：在 `defineExpose` 暴露的方法中，所有工具切换（高亮/画笔/橡皮/手势/笔记/截图）都通过这些入口协作，确保模式间互斥且副作用集中。

✅ 正确实现示例（核心代码）：
```ts
// 交互模式仅用于手势/绘图/笔记
 type PdfInteractionMode = 'hand' | 'note' | 'highlighter' | 'pen' | 'eraser-draw'
 const currentMode = ref<PdfInteractionMode>('hand')

// 独立的截图模式状态
const isScreenshotMode = ref(false)
const screenshotRect = ref<ScreenshotRect | null>(null)
const isDraggingScreenshot = ref(false)

// 打开/关闭笔记面板
const openNotePanel = () => {
  isNotePanelOpen.value = true
}

const closeNotePanel = () => {
  isNotePanelOpen.value = false
}

// 进入/退出截图模式
const enterScreenshotMode = () => {
  isScreenshotMode.value = true
  isDraggingScreenshot.value = false
  screenshotRect.value = null
}

const exitScreenshotMode = () => {
  isScreenshotMode.value = false
  isDraggingScreenshot.value = false
  screenshotRect.value = null
}

// 对外暴露的工具切换方法
defineExpose({
  // 调试面板
  toggleDebugPanel: () => {
    exitScreenshotMode()
    showDebugPanel.value = !showDebugPanel.value
  },
  // 笔记模式
  toggleNoteMode: () => {
    exitScreenshotMode()
    openNotePanel()
    currentMode.value = 'note'
  },
  // 高亮模式
  toggleHighlightMode: () => {
    exitScreenshotMode()
    closeNotePanel()
    currentMode.value = 'highlighter'
  },
  // 画笔模式
  togglePenMode: () => {
    exitScreenshotMode()
    closeNotePanel()
    currentMode.value = 'pen'
  },
  // 橡皮擦模式
  toggleEraserMode: () => {
    exitScreenshotMode()
    closeNotePanel()
    currentMode.value = 'eraser-draw'
  },
  // 手势模式
  toggleGestureMode: () => {
    exitScreenshotMode()
    closeNotePanel()
    currentMode.value = 'hand'
  },
  // 截图模式
  toggleScreenshotMode: () => {
    enterScreenshotMode()
    closeNotePanel()
    currentMode.value = 'hand' // 防止高亮/画笔拦截 pointer 事件
  },
})
```

## 测试验证
- **测试场景**：
  - 场景1：在工具栏反复切换“手势/高亮/画笔/橡皮擦/截图/笔记”，观察模式和状态：
    - 预期：
      - 进入截图模式时，`isScreenshotMode === true`，`currentMode === 'hand'`，笔记面板关闭；
      - 切回高亮/画笔/橡皮擦时，`isScreenshotMode === false`，截图矩形被清空；
      - 切到笔记模式时，右侧笔记面板打开，截图模式关闭。
  - 场景2：在截图模式中进行截图后，立刻切换到高亮模式再次绘图：
    - 预期：截图矩形不再可见，绘图工具正常工作。

- **验证方法**：
  - 方法1：在控制台打印 `currentMode` 与 `isScreenshotMode`，观察切换工具时状态变化是否符合预期。
  - 方法2：检查 `PdfPage.vue` 中是否不再出现 `currentMode === 'screenshot'` 之类的分支判断，截屏逻辑完全通过 `isScreenshotMode` 控制。

## 预防措施
- 措施1：在设计交互模式时，区分“工具类型”（如画笔/高亮/橡皮/手势）与“功能模式”（如截图、放大镜），分别管理，避免将所有状态都放入一个枚举中。
- 措施2：为所有会引起 UI 大范围变化的模式（截图/笔记/调试面板）设计统一的进入/退出函数，集中处理副作用（关闭面板、重置状态等）。
- 措施3：在代码评审中关注枚举的扩张，如果某个枚举不断被增加新值，说明其职责可能过重，需要拆分。

## 可复用经验
- 经验1：**模式解耦**：将多种交互模式（浏览、绘图、截图、笔记）拆分为不同的状态字段和入口函数，是前端复杂交互实现的关键实践。
- 经验2：**副作用集中管理**：对于“切换工具”的操作，要通过统一出口（如 `defineExpose` 中的方法）集中修改相关状态，避免到处 scattered 的 `currentMode` 与布尔 flag。
- 经验3：**渐进式重构**：本次从 `currentMode` 中抽离截图模式的过程，展示了如何在不大规模重写的情况下，通过引入新状态和函数，逐步降低旧逻辑的耦合度。
