问题序号：放大后预览高亮线条比 PDF 更粗问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：低 ~ 中
- **影响范围**：Web 端 PDF 手写高亮预览（视觉一致性）
- **发现日期**：2025-11-17
- **解决状态**：进行中（属于体验优化层面）

## 问题现象
在 Web 端 PDF 阅读器中使用手写高亮功能时：
- 在 1 倍缩放下，手写预览线条和最终 PDF 渲染出的 Ink 线条粗细视觉上比较接近。
- 在放大（例如 2 倍及以上）后进行手写：
  - 实时预览的高亮线条看起来明显比最终 PDF 中的实际高亮线条要粗；
  - 缩放越大，预览线条相对 PDF 实际线条的粗细差异越明显。
- 放大后松手，PDF 重新渲染后，高亮线条的粗细“变细了”，更接近正常阅读效果。

## 复现步骤
1. 打开 Web 端 PDF 阅读器，加载任意一份 PDF。
2. 在 100% 缩放下切换到“手写高亮”模式：
   - 在页面上画一条线，观察预览线宽与 PDF 渲染后的线宽基本接近。
3. 将 PDF 放大到 200% 或更高：
   - 在同一页上画一条类似长度的高亮线；
   - 观察实时预览层上的高亮线条比 PDF 最终渲染出的 Ink 线明显更粗。
4. 切换回 100% 再次对比预览与实际线宽，差异缩小。

## 用户体验
- 影响点1：放大后书写时，预览线条偏粗，用户很容易误以为最终 PDF 里的线也会这么粗，造成“标注太重”的错觉。
- 影响点2：预览效果和实际结果不一致，降低了对手写高亮功能的心理预期和信任感。
- 影响点3：在需要精细批注的场景（比如教辅批改），放大后希望看到“真实粗细”的预览，以便更精确控制标注。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`
- **涉及模块**：
  - 手写高亮模块（`drawStrokePreview` 预览层绘制）
  - PDF Ink 注释创建模块（`handleHighlightPointerUp` 中设置 `setBorderWidth`）

## 技术原因 (❌)
1. **预览层的 lineWidth 与 PDF 实际线宽使用了不同的计算规则**：
   - 预览层（`drawStrokePreview`）使用的是：
     ```ts
     const scale = store.scale || 1
     const baseWidth = 3
     const scaledWidth = baseWidth * Math.sqrt(scale)
     const previewLineWidth = Math.min(scaledWidth, 6)
     ctx.lineWidth = Math.max(previewLineWidth, 2)
     ```
   - PDF Ink 的真实线宽在 PointerUp 阶段按页面高度计算：
     ```ts
     const bounds = page.getBounds()
     const pageHeight = bounds[3] - bounds[1]
     const width = Math.max(pageHeight * 0.003, 1)
     ;(annot as any).setBorderWidth?.(width)
     ```
   - 两者本质上是完全独立的：
     - 预览以 `scale`（视图缩放倍数）为主因；
     - Ink 以 `pageHeight`（PDF 坐标空间尺寸）为主因，与 `scale` 无关。

2. **预览层会受到 CSS transform 的再次放大**：
   - `drawing-canvas` 与 `page` 一起被包裹在 `.viewer-inner` 中：
     ```ts
     const viewerInnerStyle = computed(() => ({
       width: `${maxWidth.value}px`,
       minHeight: `${totalHeight.value}px`,
       position: 'relative' as const,
       transform: `scale(${store.scale})`,
       transformOrigin: 'top left',
     }))
     ```
   - 也就是说：
     - `ctx.lineWidth` 在 canvas 内部是一个固定像素值（例如 3~6）；
     - 外层 `transform: scale(scale)` 再把整张画布放大一遍；
     - 当 `scale` 变大时，视觉上的线宽实际 = `ctx.lineWidth * scale`，比 PDF 实际线宽增长得更快。

3. **当前预览策略是有意“偏粗一点以保证可见性”**：
   - 为了在高倍缩放下仍然容易看到预览轨迹，预览层刻意让线稍微粗一些；
   - 但副作用是在高倍缩放下，预览与最终 Ink 的差异被放大，导致“放大后预览明显比 PDF 粗”。

## 正确实现方案 (✅)
根据需求不同，可以有不同的实现策略。当前问题属于“视觉一致性”而非“坐标错误”，所以方案侧重体验调整。

1. **方案一：预览线宽尽量贴近 PDF 实际线宽**（更真实）
   - 思路：
     - 不再让预览线宽随缩放倍数大幅变化；
     - 将 `lineWidth` 设为“接近 PDF 渲染后的屏幕效果”的固定或弱缩放值。
   - 示例：固定像素方案：
     ```ts
     // ✅ 预览线宽基本固定
     const previewLineWidth = 3
     ctx.lineWidth = previewLineWidth
     ```
   - 或者弱缩放方案：
     ```ts
     const scale = store.scale || 1
     // 相比原来的 sqrt(scale)，指数更小，且有上限
     const previewLineWidth = Math.min(3 * Math.pow(scale, 0.3), 4)
     ctx.lineWidth = previewLineWidth
     ```
   - 效果：
     - 预览线宽在不同缩放下变化幅度小，和 PDF 最终线宽更接近；
     - 高倍下预览不再显得“特别粗”。

2. **方案二：保留“偏粗预览”，但在 UI 上明确告知**（更易看见）
   - 适用场景：如果团队更重视“写的时候要非常明显”，而不太在意预览与最终线宽完全一致。
   - 做法：
     - 保持当前预览线宽的算法；
     - 在设计文档或 UI 文案中简单标注：预览仅为参考，最终线宽以 PDF 渲染为准。

3. **方案三：按 PDF 边界动态计算预览线宽**（高度一致，但实现稍复杂）
   - 思路：
     - 在 `drawStrokePreview` 中也访问 `page.getBounds()`，按 `pageHeight` 计算一个 PDF 线宽，再映射到 layout 像素；
     - 这样预览线宽和 Ink 的 `setBorderWidth` 是同一套逻辑，只是使用不同单位。
   - 简化版伪代码：
     ```ts
     const pdf = pdfDoc.value.asPDF()
     const page = pdf.loadPage(pageIndex) as mupdf.PDFPage
     const bounds = page.getBounds()
     const pageHeight = bounds[3] - bounds[1]
     const borderWidthPdf = Math.max(pageHeight * 0.003, 1)
     page.destroy()

     // 将 PDF 坐标系的宽度映射到 layout 像素
     const previewLineWidth = (borderWidthPdf / pageHeight) * layout.height
     ctx.lineWidth = previewLineWidth
     ```
   - 缺点：
     - 增加一次 `loadPage/getBounds`（可结合现有 `pageBoundsCache` 做缓存）；
     - 算法更精细，但实现和维护成本更高。

## 关键代码/公式
- **当前预览线宽算法（❌ 容易在高倍下偏粗）**：

  ```ts
  // ❌ 预览线宽随缩放增长较快，并在 transform: scale 下再次放大
  const scale = store.scale || 1
  const baseWidth = 3
  const scaledWidth = baseWidth * Math.sqrt(scale)
  const previewLineWidth = Math.min(scaledWidth, 6)

  ctx.strokeStyle = 'rgba(255, 255, 0, 0.6)'
  ctx.lineWidth = Math.max(previewLineWidth, 2)
  ```

- **PDF 实际 Ink 线宽算法（正确，但与预览无关）**：

  ```ts
  // ✅ PDF 坐标系下按页面高度计算线宽
  const bounds = page.getBounds()
  const pageHeight = bounds[3] - bounds[1]
  const width = Math.max(pageHeight * 0.003, 1)
  ;(annot as any).setBorderWidth?.(width)
  ```

- **改进示例：固定预览线宽**：

  ```ts
  // ✅ 预览线宽基本固定，缩放时粗细感受接近真实 PDF
  const previewLineWidth = 3
  ctx.lineWidth = previewLineWidth
  ```

## 测试验证
- **测试场景**：
  - 场景1：1 倍缩放下短线绘制
    - 步骤：在 100% 缩放下画一条短线；
    - 预期：预览线宽与 PDF 渲染后的线宽相差不大，视觉一致。
  - 场景2：2 倍缩放下长线绘制
    - 步骤：放大到 200%，画一条长线；
    - 预期：预览线条粗细与最终 PDF 渲染线条接近，不再出现明显“预览比 PDF 粗很多”的感觉。
  - 场景3：0.75 倍缩放下绘制
    - 步骤：缩小到 75%，画线；
    - 预期：预览线条在缩小时也不会显得过细或难以辨认。

- **验证方法**：
  - 方法1：截图对比
    - 对同一条线的预览状态和最终 PDF 渲染状态进行截图对比，检查不同缩放下线宽差异。
  - 方法2：像素量测
    - 使用开发者工具或图像编辑器测量预览线宽与 PDF 线宽的像素差距，确认是否满足预期范围。

## 预防措施
- 措施1：在设计预览层时，明确预览与真实渲染之间的目标关系（是“尽量一致”还是“偏向易见性”）。
- 措施2：在涉及多坐标系（PDF 坐标 / layout 坐标 / transform 缩放）的场景下，尽量将“视觉缩放”统一交给 CSS transform，逻辑计算只在一个坐标系中进行，减少叠加效应。
- 措施3：对预览相关的参数（如 lineWidth）进行缩放敏感性评估，在高倍缩放场景下提前压制过大的参数增长。

## 可复用经验
- 经验1：在有“预览层”和“最终渲染层”的场景中，必须分别明确两者的视觉目标，不要默认它们在所有维度上都一致。
- 经验2：当存在多层缩放（canvas 内缩放 + CSS transform 缩放）时，需要检查参数是否被放大多次，尤其是线宽、阴影等对性能和视觉影响较大的属性。
- 经验3：对用户来说，比起绝对精确的一致性，通常更重要的是“预期稳定”：同一缩放下预览与结果大致一致，并且在不同缩放下差异是可解释、可预期的。
