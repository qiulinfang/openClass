问题2：加入课堂后重复弹出原生教室选择框问题

## 问题元信息
- **问题分类**：`其他`
- **严重程度**：`高`
- **影响范围**：`加入课堂/投屏链路；原生 ScreenCastingCommunicator 启动通信时的 UI 行为`
- **发现日期**：`2025-12-26`
- **解决状态**：`已解决`

## 问题现象
- Web 点击“加入课堂”已经能弹出原生 `ClassroomSelectionDialog` 后，进入加入课堂流程时可能出现：
  - **用户已经在 Web 触发并完成一次选择**，但加入后原生通信层（ScreenCastingCommunicator）又**自动弹出一次相同 Dialog**。
- 造成“重复选择”“流程被打断”的体验问题。

## 复现步骤
1. Web 点击“加入课堂”，弹出原生 `ClassroomSelectionDialog`。
2. 在 Dialog 中完成城市/学校/教室选择并确认。
3. Web 调用 `joinClassroom` 后，原生开始投屏/通信初始化。
4. 观察：原生又再次弹出 `ClassroomSelectionDialog`（第二次）。

## 用户体验
- 重复操作：需要再次选择教室，用户会困惑。
- 流程打断：可能导致加入课堂状态与投屏启动时机异常。
- 可用性下降：用户可能以为加入失败或系统卡死。

## 相关文件/模块
- **涉及文件**：
  - `app/src/main/java/com/cosinetech/imates/screencasting/ScreenCastingCommunicator.java`：启动通信时无条件弹出选择框。
  - `app/src/main/java/com/cosinetech/imates/screencasting/ScreenCastingManager.java`：投屏/课堂全局状态管理（新增缓存字段）。
  - `app/src/main/java/com/cosinetech/imates/ui/webview/common/WebAppInterface.java`：Web 触发选择框并把选择结果写入缓存。
- **涉及模块**：
  - screencasting 通信初始化（组播/心跳/设备注册）
  - 原生 Dialog 显示逻辑

## 技术原因 (❌)
1. `ScreenCastingCommunicator.start()` 内存在无条件逻辑：
   - `deviceClientWrapper.showClassroomSelectionDialog(...)`
   - 与 Web 侧发起的选择框行为叠加，导致“二次弹窗”。
2. 原生通信层没有复用“已选择的教室位置”，导致它认为必须再选一次。

❌ 错误代码示例（简化）
```java
// ScreenCastingCommunicator.start()
// 2. 获取所有教室并显示选择Dialog
deviceClientWrapper.showClassroomSelectionDialog(new DeviceClientWrapper.OnClassroomSelectedListener() {
  public void onSelected(String city, String school, ClassroomInfo classroom) {
    deviceClientWrapper.register(getLocalIpAddress());
    deviceClientWrapper.startHeartbeat();
  }
});
```

## 正确实现方案 (✅)
1. **在 ScreenCastingManager 增加“已选教室位置缓存”**：
   - `selectedCity/selectedSchool/selectedClassroom` + setter/getter。
2. **Web 触发选择完成后写入缓存**：
   - 在 `WebAppInterface.showClassroomSelectionDialog` 的 `onSelected` 回调中调用 `ScreenCastingManager.setSelectedClassroomLocation(...)`。
3. **修改 ScreenCastingCommunicator 启动逻辑**：
   - 若缓存存在（city/school/classroom 都非空），则直接：
     - `deviceClientWrapper.setLocation(city, school, classroom)`
     - `register + startHeartbeat`
     - **不再弹 Dialog**
   - 若缓存为空，保持原来“弹 Dialog 选择”作为兜底路径。

✅ 正确代码示例（简化）
```java
// ScreenCastingCommunicator.start()
String city = ScreenCastingManager.getSelectedCity();
String school = ScreenCastingManager.getSelectedSchool();
String classroom = ScreenCastingManager.getSelectedClassroom();

if (city != null && !city.isEmpty() && school != null && !school.isEmpty() && classroom != null && !classroom.isEmpty()) {
  deviceClientWrapper.setLocation(city, school, classroom);
  deviceClientWrapper.register(getLocalIpAddress());
  deviceClientWrapper.startHeartbeat();
} else {
  deviceClientWrapper.showClassroomSelectionDialog(/* fallback */);
}
```

## 测试验证
- **测试场景**：
  - 场景1：Web 触发原生选择框并完成选择后，进入加入课堂流程，确认不再出现第二次弹框。
  - 场景2：缓存为空时（例如从非 Web 流程启动 screencasting），仍会弹框进行选择，功能不回退。
- **验证方法**：
  - 方法1：手动跑通“加入课堂→投屏准备”流程，观察只弹一次 Dialog。
  - 方法2：Logcat 搜索关键日志（例如 `Use selected classroom from Web`）确认复用缓存分支生效。

## 预防措施
- 措施1：对“UI 弹窗”做单一职责归属：同一业务流程只能由一个入口负责弹窗，其他层只消费结果。
- 措施2：投屏/加入课堂流程增加状态机或显式参数传递，避免隐式重复动作。
- 措施3：对关键流程加 traceId/埋点，便于发现“重复弹窗/重复执行”。

## 可复用经验
- 经验1：混合链路（Web→原生→通信层）中，必须明确“数据来源唯一”，避免多个层级重复获取/重复交互。
- 经验2：当原生已有可复用选择结果时，通信层应尽量无 UI，避免在后台初始化阶段打断用户。
- 经验3：设置 fallback 分支（缓存为空才弹框）可保证兼容旧路径。
