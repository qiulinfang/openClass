# 20251212 投屏（screencasting）文档合并（含 Web↔原生时序）

> 本文档合并自：

> - `.specstory/sum/20251212_screencasting包功能使用分析.md`

> 并补充：`Web → WebAppInterface → ScreenCastingManager → Web` 的最新闭环时序（老师命令控制投屏）。

## 1. 背景与问题

产品希望将 `com.cosinetech.imates.screencasting` 模块的原生 UI（教室选择对话框、课堂开关按钮、悬浮窗等）迁移到 WebView 中实现。但现有实现存在：

- 原生与 Web 状态不同步的风险
- 业务逻辑误迁移到 Web 导致推流/网络异常的风险
- JS Bridge（Web↔原生）调用与回调规范缺失

此外，Web 侧开展课堂功能需要调用 `androidBridge.joinClassroom/exitClassroom`，团队曾缺乏明确资料确认它是否与原生入口行为一致，导致对照代码成本高。

## 2. 目标与边界（必须明确）

### 2.1 目标

- Web 端统一课堂 UI（教室选择、加入/退出课堂按钮、投屏状态展示等）
- 原生侧保留能力层（编码、推流、网络通信、命令处理），保证稳定性
- 建立清晰的双向通信：
  - Web → 原生：加入/退出课堂、获取课堂状态、获取教室树
  - 原生 → Web：课堂状态变化、投屏开始/停止、错误提示

### 2.2 边界（重要约束）

- **投屏开始/停止由老师端命令驱动**（学生端不应由 Web 主动 start/stop 投屏）
- `screencasting` 包中不应直接 new 或弹出 Web 依赖的 UI（如 Dialog）；UI 迁移后应通过接口返回数据给 Web
- 游客模式与正式模式的判定应统一在桥接层（`WebAppInterface`）

## 3. 相关模块与文件

### 3.1 原生侧

- `app/src/main/java/com/cosinetech/imates/screencasting/ScreenCastingManager.java`
  - 课堂状态机
  - 命令处理回调（StartProjection/StopProjection）
  - 转发开关控制（通过 `UdpForwarder`）
- `app/src/main/java/com/cosinetech/imates/screencasting/ScreenCastingCommunicator.java`
  - UDP 组播/单播通信
  - 周期性状态上报
  - 接收老师端投屏/截图等命令并分发给 `CommandHandler`
- `app/src/main/java/com/cosinetech/imates/screencasting/UdpForwarder.java`
  - 接收本地 TS 数据并转发至老师端/PC 目标地址
- `app/src/main/java/com/cosinetech/imates/screencasting/H264MpegTSStreamerManager.java`
  - H264 → TS 推流组件管理
- `app/src/main/java/com/cosinetech/imates/ui/webview/common/WebAppInterface.java`
  - WebView JS Bridge
  - 提供 `joinClassroom/exitClassroom/getClassroomStatus/fetchClassroomTree` 等接口
  - 执行 JS 回调（`executeJavaScript`）

### 3.2 Web 侧

- `imates-web/src/views/MyProfileView.vue`
  - Web UI 入口：加入/退出课堂、展示课堂状态
- `imates-web/src/services/business/android-bridge.ts`
  - `window.AndroidBridge` 的 TypeScript 封装
  - 事件监听：`onClassroomJoined/onClassroomExited/onClassroomStatusChanged/onScreenProjectionStarted/onScreenProjectionStopped`

## 4. 统一结论：Web 入口与原生入口的一致性

- `WebAppInterface.joinClassroom/exitClassroom` **复用原生能力层**（`ScreenCastingManager`、`ScreenShareKit`、`H264MpegTSStreamerManager` 等），目标是与原生入口（如 `MyProfileActivity`/悬浮窗入口）保持一致。
- 区别在于：`WebAppInterface` 额外增加了向 Web 通知状态的能力（JS 回调）。

### 4.1 游客模式

- 沿用 `ApplicationModelShared.fakeClassMode`
- Web 可显示“已加入课堂”，但不触发真实投屏

### 4.2 正式模式

- UI 线程初始化 `ScreenShareKit`
- H264 数据回调中喂给 TS 流组件（H264→TS）
- 成功后设置 `ScreenCastingManager.setClassMode(true)` 进入课堂控制状态

## 5. Web↔原生接口与事件（建议作为协议对照表）

### 5.1 Web → 原生（JS Bridge）

- `joinClassroom(studentId, studentName, isGuest)`
- `exitClassroom()`
- `getClassroomStatus()`
- `fetchClassroomTree()`

> 说明：在“老师命令控制投屏”模型下，Web 侧应**不依赖** `startScreenProjection/stopScreenProjection/setClassroomMode` 作为入口能力。

### 5.2 原生 → Web（回调事件）

- `window.onClassroomJoined(statusJson)`
- `window.onClassroomExited()`
- `window.onClassroomError(message)`
- `window.onScreenProjectionStarted()`
- `window.onScreenProjectionStopped()`
- `window.onClassroomStatusChanged(statusJson)`（可选，但推荐用于 UI 同步）

## 6. 关键状态字段（单一事实源）

- `ScreenCastingManager.isHavingClass()`：是否处于课堂模式（是否需要启动 communicator 并等待老师命令）
- `ScreenCastingManager.isProjecting()`：是否应投屏（由老师命令 Start/Stop 控制）

建议 Web 的展示状态至少区分：
- `ready`：已在课堂中，但老师未要求投屏
- `streaming`：老师要求投屏，正在转发 TS 数据

## 7. 核心时序：Web → WebAppInterface → ScreenCastingManager → Web（老师命令控制投屏）

### 7.1 加入课堂

1. Web（`MyProfileView.vue`）点击“加入课堂”
2. Web 调用 `androidBridge.joinClassroom(...)`
3. 原生 `WebAppInterface.joinClassroom(...)`
   - 正式模式：初始化 `ScreenShareKit`，启动 TS 流，设置 `ScreenCastingManager.setClassMode(true)`
   - 然后 `executeJavaScript` 触发：
     - `window.onClassroomJoined({isInClass:true,isProjecting:false,status:"ready",...})`

### 7.2 老师命令驱动投屏开始

1. 老师端下发投屏命令（投屏名单包含当前学生）
2. 学生端 `ScreenCastingCommunicator` 收到消息并触发：
   - `CommandHandler.onStartProjection()`
3. `ScreenCastingManager` 的命令处理：
   - `bShouldProjection = true`
   - `udpForwarder.setForwardingEnabled(true)`
   - 触发 `notifyProjectionStateChanged(true)`
4. `WebAppInterface`（注册了 `ProjectionStateListener`）收到回调后：
   - `executeJavaScript("if(window.onScreenProjectionStarted){window.onScreenProjectionStarted();}")`
   - （可选）`executeJavaScript("if(window.onClassroomStatusChanged){window.onClassroomStatusChanged({isInClass:true,isProjecting:true,status:'streaming'});}")`
5. Web 侧监听到 `onScreenProjectionStarted` 后把 UI 状态 `isProjecting=true`

### 7.3 老师命令驱动投屏停止

与上面对应：

- `CommandHandler.onStopProjection()`
- `bShouldProjection=false` + `udpForwarder.setForwardingEnabled(false)`
- 原生回调 `window.onScreenProjectionStopped()`
- Web UI 同步 `isProjecting=false`

## 8. 测试验证

### 8.1 场景

- 场景 1：游客账号加入课堂
  - 期望：只切 `fakeClassMode`，不触发真实投屏；Web 收到 `onClassroomJoined`
- 场景 2：正式账号加入课堂
  - 期望：初始化 `ScreenShareKit` 并进入课堂模式；Web 收到 `onClassroomJoined(status=ready)`
- 场景 3：老师端发送 StartProjection
  - 期望：`ScreenCastingManager` 收到 `StartProjection`，`UdpForwarder` 开转发；Web 收到 `onScreenProjectionStarted`，UI 变为投屏中
- 场景 4：老师端发送 StopProjection
  - 期望：停止转发；Web 收到 `onScreenProjectionStopped`，UI 变为未投屏

### 8.2 验证方法

- 方法 1：Logcat 观察：
  - `ScreenCastingManager` 是否打印 `Received command: StartProjection/StopProjection`
  - `WebAppInterface` 是否打印/回传日志（`sendLogToWeb`）
- 方法 2：Web 控制台观察：
  - 是否收到 `onClassroomJoined/onScreenProjectionStarted/onScreenProjectionStopped`

## 9. 预防措施与规范建议

- 所有 UI 相关调用统一走 JS Bridge（数据返回 + Web 渲染），避免在底层 SDK 创建视图
- Bridge API 建议版本化（或至少建立对照表），防止 Web 与原生协议不一致
- 课堂状态变更（加入/退出/投屏开始停止）需要同步更新本文档
