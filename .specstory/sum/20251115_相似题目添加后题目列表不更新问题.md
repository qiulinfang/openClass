问题序号：相似题目添加后题目列表不更新问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`中`
- **影响范围**：`练习页题目列表与相似题目联动`
- **发现日期**：`2025-11-15`
- **解决状态**：`已解决`

## 问题现象
通过「举一反三」查找到相似题目后，点击相似题目列表中的「添加到第一题位置」按钮：
- 控制台能看到 `111 / 222 / 333` 等调试日志；
- 也能看到 `questionStore.ts` 中 `444 / 555` 日志，表示 `addSimilarQuestionToList` 被调用；
- 但练习页左侧题目列表看起来没有变化，用户感觉题目没有被添加成功。

## 复现步骤
1. 打开 `ExerciseSolveView`，选中一题。
2. 切到「举一反三」页签，点击查找相似题目。
3. 在 `SimilarQuestionList` 中点击某条相似题目的「添加到第一题位置」按钮。
4. 观察控制台日志及左侧题目列表变化。

## 用户体验
- 影响点1：用户点击「添加」后看不到明显变化，以为操作失败。
- 影响点2：题目实际已经进入列表但位置不直观，增加理解成本。
- 影响点3：刷新/切换后列表数据可能与预期不一致，降低信任感。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/SimilarQuestionList.vue`：相似题目列表 UI 和交互逻辑。
  - `imates-web/src/stores/questionStore.ts`：题目列表 `questions` 的 Pinia Store 管理，包括 `addSimilarQuestionToList` 等方法。
  - `imates-web/src/views/ExerciseSolveView.vue`：练习页面主视图，负责联动题目列表与相似题目组件。
- **涉及模块**：
  - `questionStore`：题目列表状态与持久化逻辑。
  - `SimilarQuestionList`：相似题目查找和添加入口。

## 技术原因 (❌)
1. 原因1：`addSimilarQuestionToList` 最初使用 `questions.value.push(question)` 将相似题目追加到列表尾部，而 UI 文案是「添加到第一题位置」，造成预期与现实不一致。
2. 原因2：`addSimilarQuestionToList` 调用时未传入 `subject` 参数，导致不会调用保存到 IndexedDB 的逻辑，刷新或重新加载后新增题目可能丢失。
3. 原因3：去重逻辑与存在性判断中，初始使用 `id` 判断，而相似题目的 `id` 字段可能为空或与原题不一致，需要改为使用业务上稳定的 `bmNo` 字段。

❌ 错误/不完整实现示例：
```typescript
// questionStore.ts 中的初始实现（简化版）
const addSimilarQuestionToList = async (question: ExerciseItem, subject?: string): Promise<void> => {
  // 仅通过 id 判断是否存在
  const exists = questions.value.some(q => q.id === question.id)
  if (!exists) {
    // 追加到列表末尾
    questions.value.push(question)
    // 未传 subject 时不会保存本地
    if (subject) {
      await saveQuestionsToLocal(subject)
    }
  }
}

// SimilarQuestionList.vue 中的调用
const addToMyList = async (question: any) => {
  ...
  // 未明确传 subject，或 subject 为空
  questionStore.addSimilarQuestionToList(question)
  ...
}
```

## 正确实现方案 (✅)
1. 方案1：将 `addSimilarQuestionToList` 从 `push` 改为 `unshift`，保证相似题目插入列表首位，与「添加到第一题位置」文案一致。
2. 方案2：从当前题目或相似题目对象中推导 `subject` 并显式传入 `addSimilarQuestionToList`，在内部统一调用 `saveQuestionsToIndexedDB(subject, questions.value)` 持久化。
3. 方案3：存在性判断改为基于 `bmNo` 字段（或其他稳定业务主键），并在添加时补全题目的 `subject` 字段，保证后续读取和保存逻辑一致。

✅ 修正后的关键代码示例：
```typescript
// questionStore.ts
const addSimilarQuestionToList = async (question: ExerciseItem, subject?: string): Promise<void> => {
  console.log('444:', question)
  console.log('454545questions:', questions.value)

  // 使用 bmNo 判断是否已存在
  const exists = questions.value.some(q => q.bmNo === question.bmNo)
  console.log('555:', exists)

  if (!exists) {
    // 确保题目带有学科字段
    const normalizedSubject = (subject || question.subject || 'math').toLowerCase()
    question.subject = normalizedSubject

    // 插入到列表首位
    questions.value.unshift(question)

    // 持久化到 IndexedDB
    if (subject) {
      try {
        await saveQuestionsToIndexedDB(subject, questions.value)
      } catch (error) {
        console.error('[QUESTION] ❌ 保存题目列表到 IndexedDB 失败:', error)
      }
    }
  }
}

// SimilarQuestionList.vue
const addToMyList = async (question: any) => {
  if (!question) return
  try {
    addingIds.value.add(question.id)
    // 从当前题目推导学科
    const subject = currentQuestion.value?.subject || ''
    await questionStore.addSimilarQuestionToList(question, subject)
    emit('questionAdded')
  } finally {
    addingIds.value.delete(question.id)
  }
}
```

## 关键代码/公式
- 代码片段1：基于 `bmNo` 字段的存在性判断和去重逻辑。
- 代码片段2：`unshift` 插入题目到列表顶部的实现，保证 UI 与行为一致。
- 代码片段3：直接使用 `saveQuestionsToIndexedDB(subject, questions.value)` 进行持久化，取代中间包装函数。

## 测试验证
- **测试场景**：
  - 场景1：从无相似题目开始，查找并添加一条相似题目，确认它出现在题目列表第一条，并且刷新页面后仍然存在。
  - 场景2：对同一条相似题目多次点击「添加」，确认仅添加一次，控制台 `exists` 日志为 `true`，列表无重复。
  - 场景3：切换学科或重新进入练习页，确认 IndexedDB 中的数据被正确加载，新增题目仍在列表中。
- **验证方法**：
  - 方法1：通过浏览器 DevTools 观察 `questions` 数组变化，确认新增题目的位置和内容。
  - 方法2：刷新页面后再次查看题目列表，确认数据由 IndexedDB 正确恢复。

## 预防措施
- 措施1：对「追加」「插入到顶部」等 UI 文案与实际行为进行对齐评审，避免语义不一致。
- 措施2：明确业务主键字段（如 `bmNo`）并在所有去重/存在性判断中统一使用。
- 措施3：对涉及本地持久化的操作，统一使用封装良好的 API（如 `saveQuestionsToIndexedDB`），减少分散的 helper 函数。

## 可复用经验
- 经验1：当 UI 操作有明确语义（如「移动到顶部」「添加到第一题」）时，代码实现应直接反映该语义，避免用户误解。
- 经验2：在使用 `v-html` / 异步数据渲染的场景下，调试日志（如 `444/555`）可以帮助快速确认方法是否被调用以及调用参数。
- 经验3：本地持久化逻辑应集中封装，统一错误处理和日志输出，降低维护成本。
