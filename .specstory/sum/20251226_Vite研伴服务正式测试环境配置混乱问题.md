```markdown
问题序号：Vite研伴服务正式测试环境配置混乱问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`中`
- **影响范围**：`imates-web 本地开发联调；所有走 Vite proxy 的接口（/admin、/permission、/ai、/biologyTopicKnowledge 等）`
- **发现日期**：`2025-12-22`
- **解决状态**：`待解决`

## 问题现象
在 `imates-web/vite.config.ts` 中，研伴/学班服务的代理目标地址通过 `mode` 进行“测试/正式”切换，但实际配置与注释、联调期望不一致，导致：
- 开发时不确定当前请求到底打到哪台服务器（端口 9222 / 58443）
- 临时需要“强制走正式服”时容易改错或改漏
- 资源服务器 `RESOURCE_FILE_BASE` 的测试/正式切换语义也容易被误改为“固定同一个地址”

本次对话中，用户提出“现在暂时改一下，vite中的研伴使用正式服务器”，说明现有配置在联调阶段不够直观。

## 复现步骤
1. 在本地启动 Vite：
   - `vite`（默认 mode）
   - `vite --mode test`
2. 观察 `vite.config.ts` 中 `EDU_SERVICE_BASE`、`RESOURCE_FILE_BASE` 的取值。
3. 访问依赖代理的接口（例如 `/biologyTopicKnowledge/knowledgeTopicAndAck2`）。
4. 发现请求目标地址与期望不一致，或需要反复修改配置才能命中正确环境。

## 用户体验
- 联调效率降低：频繁出现“请求打错环境”的时间浪费。
- 排查困难：同一套前端代码，不同开发者可能用不同 mode，导致问题无法复现。
- 配置不确定性：紧急联调时容易误把测试环境当正式环境。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/vite.config.ts`：
    - `EDU_SERVICE_BASE` 环境切换
    - `RESOURCE_FILE_BASE` 环境切换
    - `server.proxy` 中 `/admin`、`/permission`、`/ai`、`/biologyTopicKnowledge` 等均依赖 `EDU_SERVICE_BASE`
- **涉及模块**：
  - Vite dev server proxy

## 技术原因 (❌)
1. **配置语义与注释不一致**：例如注释说明 `mode=test` 应使用某端口，但代码实际在 `isTest` 分支使用另一端口，产生理解偏差。
2. **环境切换粒度过粗**：仅用 `mode=test` 开关不足以覆盖“临时强制打某环境”的需求。
3. **缺少单一可信的环境标识**：开发时没有一个明确的、可被 UI/日志/页面直接感知的“当前环境”信息源。

（问题示例：同一段配置在联调时经常被临时改动，且容易改漏）
```ts
// ❌ 典型问题：联调时需要临时强制走某环境，但配置是多处依赖变量，且注释可能误导
const EDU_SERVICE_BASE = isTest
  ? 'http://www.imates.com.cn:58443/blw-edu-service-alc'
  : 'http://www.imates.com.cn:9222/blw-edu-service-alc'

proxy: {
  '/admin': { target: EDU_SERVICE_BASE },
  '/permission': { target: EDU_SERVICE_BASE },
  '/ai': { target: EDU_SERVICE_BASE },
  '/biologyTopicKnowledge': { target: EDU_SERVICE_BASE },
}
```

## 正确实现方案 (✅)
1. **统一明确环境定义**：在文件顶部用“正式/测试”的明确定义（端口、域名）并保证注释与代码一致。
2. **提供强制开关**：支持通过环境变量或启动参数强制指定后端，例如：
   - `VITE_EDU_SERVICE_BASE=http://...` 覆盖默认值
3. **增强可观测性**：
   - 保留启动日志（已存在）
   - 在页面（或调试面板）显示当前环境/target
4. **避免误改 RESOURCE_FILE_BASE**：测试/正式资源域名差异需要有明确注释与约束，避免被临时改成同一个值。

（建议实现示例：允许 env 覆盖）
```ts
// ✅ 优先读环境变量，便于临时联调，不需要改代码
const EDU_SERVICE_BASE = process.env.VITE_EDU_SERVICE_BASE || (isTest ? TEST_BASE : PROD_BASE)
```

## 关键代码/公式
- Vite proxy 依赖 `EDU_SERVICE_BASE` 的入口：
```ts
// imates-web/vite.config.ts
'/admin': { target: EDU_SERVICE_BASE },
'/permission': { target: EDU_SERVICE_BASE },
'/ai': { target: EDU_SERVICE_BASE },
'/biologyTopicKnowledge': { target: EDU_SERVICE_BASE },
```

## 测试验证
- **测试场景**：
  - 场景1：默认启动（非 test mode）应命中“正式”定义
  - 场景2：`--mode test` 启动应命中“测试”定义
  - 场景3：设置 `VITE_EDU_SERVICE_BASE` 时应覆盖 mode 的默认选择
- **验证方法**：
  - 方法1：观察启动日志 `EDU_SERVICE_BASE` 输出
  - 方法2：在 Network 面板确认请求 Host/Port

## 预防措施
- 将环境定义抽成常量，并把端口含义写清楚（正式/测试）。
- 引入 `.env.test` / `.env.development` 中的明确配置，并在 `vite.config.ts` 读取。
- 在 PR/评审中禁止“临时硬编码环境地址”直接提交到主分支。

## 可复用经验
- 联调环境切换必须支持“无代码改动”的方式（env 覆盖优于硬编码）。
- 注释必须与配置一致，否则会成为误导源。
- 代理目标的可观测性（日志/界面）能显著降低排查成本。
