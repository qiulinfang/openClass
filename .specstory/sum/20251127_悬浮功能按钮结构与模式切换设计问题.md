问题序号：悬浮功能按钮结构与模式切换设计问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`中`
- **影响范围**：`主页悬浮功能按钮、右侧聊天面板与统一聊天对话框的入口交互`
- **发现日期**：`2025-11-27`
- **解决状态**：`已解决`

## 问题现象
主页右下角悬浮功能按钮（原 q-fab + q-fab-action）在需求演进过程中出现了以下问题：
- 既要提供草稿本、AI 聊天等多个入口，又要支持右侧聊天面板（MainChatPanel）与全屏对话框（UnifiedChatDialog）之间的模式切换。
- FAB 结构过于复杂（多层 q-fab-action），代码和交互都显得臃肿；在设计调整后，需求变为只保留“与 AI 聊天”入口，并且进一步希望改为**单一悬浮按钮**。
- 在右侧聊天面板已打开时，悬浮按钮仍然显示，造成 UI 和交互上的冲突。
- 最终还要求完全去除 q-fab，使用原生 button 手动实现悬浮按钮样式与拖拽逻辑。

## 复现步骤
1. 打开应用首页（MainView.vue 对应的 /app/... 路由）。
2. 观察右下角悬浮按钮：
   - 初始为 q-fab，包含多个 q-fab-action（草稿本、与 AI 聊天）。
3. 点击“与 AI 聊天”或其他入口时：
   - 同时存在右侧面板、统一聊天对话框、草稿本等入口，交互关系不清晰。
4. 在右侧聊天面板已打开的情况下，悬浮按钮仍可见且可点击，视觉与交互都不合理。

## 用户体验
- 悬浮按钮职责不清晰：既是功能菜单，又是聊天入口，易造成用户困惑。
- 在右侧面板已打开时仍显示悬浮按钮，会给人“重复入口”的感觉，界面略显杂乱。
- FAB 的展开、图标、子 action 等 Quasar 默认交互已不再符合新的简化设计。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/views/MainView.vue`：悬浮按钮 DOM 结构、拖拽逻辑、聊天面板与对话框的入口控制。
  - `imates-web/src/components/MainChatPanel.vue`：右侧聊天面板，提供 `toggle-mode` 事件切换到统一聊天对话框。
  - `imates-web/src/components/UnifiedChatDialog.vue`：全屏聊天对话框，作为 AI 聊天主入口。
- **涉及模块**：
  - UI 交互：主页悬浮按钮、右侧聊天面板、统一 AI 聊天对话框。
  - 状态管理：`uiStore.showAIChatDialog`、`showMainChatPanel`。

## 技术原因 (❌)
1. **悬浮按钮职责堆叠**：
   - 同一个 FAB 同时承载草稿本、AI 聊天、多入口展开等职责，缺乏清晰的单一职责设计。
2. **显示条件缺乏统一约束**：
   - `showFab` 只根据路由判断（是否在 exerciseSolve / drawingBoard），未考虑右侧聊天面板的显示状态，导致面板打开时 FAB 仍显示。
3. **过度依赖 Quasar FAB 组件形态**：
   - 使用 q-fab + q-fab-action 的展开式结构，在需求简化后反而成为负担，难以实现更扁平的自定义样式与行为。

错误结构示例（早期版本示意）：
```vue
<q-fab
  icon="add"
  direction="up"
  color="purple"
  padding="md"
>
  <q-fab-action @click="handleDraftClick" icon="edit_note" label="草稿本" />
  <q-fab-action @click="handleAIChatClick" icon="chat" label="与AI聊天" />
</q-fab>
```

## 正确实现方案 (✅)
1. **简化悬浮按钮职责**：
   - 悬浮按钮仅作为“主页 AI 聊天入口”，只负责切换右侧 MainChatPanel 的显隐。
2. **手动实现悬浮按钮样式和行为**：
   - 去掉 q-fab，使用原生 `button` + 自定义样式，实现圆形、阴影、拖拽等效果。
3. **统一显示条件**：
   - `showFab` 同时考虑路由与面板状态：
     - 非 exerciseSolve、非 drawingBoard 页面；
     - 且 `showMainChatPanel === false`。

关键实现示例：
```vue
<!-- MainView.vue 模板片段 -->
<div 
  v-if="showFab"
  class="floating-fab"
  :style="fabStyle"
  @mousedown="startDrag"
  @touchstart="startDrag"
>
  <button
    type="button"
    class="floating-fab-btn"
    @click.stop="showMainChatPanel = !showMainChatPanel"
  >
    <span class="material-icons">chat_bubble</span>
  </button>

  <!-- 引导气泡保留 -->
  <div v-if="shouldShowGoResourcesHint && showGoResourcesBubble" class="go-resources-bubble">
    ...
  </div>
</div>

// 悬浮按钮显示条件
const showFab = computed(() => {
  const isRouteAllowed = route.name !== 'exerciseSolve' && route.name !== 'drawingBoard'
  return isRouteAllowed && !showMainChatPanel.value
})
```

## 测试验证
- **测试场景**：
  - 场景1：在知识图谱、资源下载等页面，悬浮按钮显示，点击可打开 / 关闭右侧 MainChatPanel。
  - 场景2：在 exerciseSolve、drawingBoard 页面，悬浮按钮始终不显示。
  - 场景3：当 MainChatPanel 打开时，悬浮按钮自动隐藏；关闭面板后重新出现。
- **验证方法**：
  - 手动切换各路由观察 FAB 显示；
  - 多次打开/关闭面板，确认 FAB 与面板状态互斥。

## 预防措施
- 悬浮按钮只负责单一入口职责，后续如需增加新功能入口，应使用导航栏或工具箱等位置，不再累加在 FAB 上。
- 所有全局入口组件（FAB、抽屉、面板）在设计时统一考虑“显示条件 + 状态依赖”，避免多入口叠加。
- 若未来再引入 UI 框架组件（如 q-fab），先确认其交互模式是否符合当前产品设计，避免后期大幅重构。

## 可复用经验
- 悬浮入口类组件应保持职责单一，与其它入口（面板、对话框）建立清晰的状态关系。
- 在 Vue 中通过 `computed` 统一管理显示条件，比在模板中散布 `v-if` 更便于维护。
- 对交互要求较高的组件（拖拽、位置记忆等），使用原生元素 + 定制样式往往比重度依赖 UI 框架组件更灵活。
