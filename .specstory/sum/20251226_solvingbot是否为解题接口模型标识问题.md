问题序号：solvingbot是否为解题接口模型标识问题

## 问题元信息

- **解决状态**：`已解决`

## 问题现象
在排查/理解“解题接口”调用链路时，出现疑问：`solvingbot` 是否就是解题接口实际调用的“模型接口/模型名称”。由于命名上类似“模型代号”，容易误以为它与具体大模型（如某个 provider 的 modelName）一一对应。

## 复现步骤
1. 在前端/后端配置或请求体中看到字段/参数值为 `solvingbot`。
2. 将其直观理解为“正在调用的具体大模型名称”。
3. 在需要确认实际模型（如 GPT/DeepSeek/Qwen）或排查路由时，无法从 `solvingbot` 直接得出确定结论。

## 用户体验
- 容易把 `solvingbot` 当成“模型名”，导致排查方向偏差
- 无法快速确认实际调用的 provider/modelName，降低定位效率
- 配置/联调沟通成本增加（前端、后端、算法/平台之间）

## 技术原因 (❌)
1. `solvingbot` 的命名语义偏“模型代号”，但在很多系统里它实际是**业务 Bot/Agent 的标识**（botId/scene），而不是 provider 的真实 `modelName`。
2. 调用链路可能是“前端传 botId -> 后端/网关选择模型 + 拼 prompt -> 调用 LLM provider”，因此仅凭 `solvingbot` 无法确定最终模型。
3. 缺少统一约定/文档：
   - `botId/scene` 与 `modelName` 的职责边界不清
   - 请求体/日志中未显式打印最终路由到的真实模型信息

```text
❌ 典型误解：
- 看到 model=solvingbot
- 直接认为 solvingbot == 某个具体大模型

（实际更常见：solvingbot 是业务 bot 名称，后端再路由到真实 provider/modelName）
```

## 正确实现方案 (✅)
1. 明确概念分层：
   - `solvingbot`：业务侧 Bot/场景标识（用于选择提示词、工具、流程编排等）
   - `modelName`/`llmModel`：真实大模型名称（用于最终调用某个 provider 的模型）
2. 在接口/日志中补齐可观测性（推荐）：
   - 后端在响应/日志中回传或打印 `resolvedModelName`（最终选择的真实模型名）
   - 若有灰度/动态路由，也应记录路由决策
3. 前端排查方式：
   - 搜索 `solvingbot` 在请求体中对应的字段含义（`model` / `botId` / `scene`）
   - 若同时存在 `modelName` 等字段，以 `modelName` 为准

```text
✅ 推荐理解：
- solvingbot 更像“解题机器人/解题场景”的入口标识
- 最终调用哪个大模型，需要看后端/网关的映射与路由结果
```
