问题序号：PDF 截图缩放偏移与截图问答模式问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：中
- **影响范围**：PDF 查看页截图问答功能，影响所有使用截图向 AI 提问的用户
- **发现日期**：2025-11-18
- **解决状态**：已解决

## 问题现象
- 在 PDF 页面缩放（放大或缩小）后进行区域截图：
  - 截图图片中的内容与用户在 PDF 上框选的区域对齐，但蓝色截图框本身在页面上存在偏移。
  - 缩小时蓝框偏左上；放大时蓝框偏右下。
- 修正蓝框偏移后，发现新的现象：
  - 无论放大、缩小或不缩放，截出的图片高度总是比框选的高度小。
  - 框选高度越大，“缺失”的高度越大，垂直方向漏掉的内容越多。
- 在截图问答模式下：
  - 轻轻点击或很小范围的拖动也会触发截图并弹出截图问答对话框，误触发频繁。

## 复现步骤
1. 打开 PDF 查看页面，进入截图模式。
2. 对 PDF 页面进行不同倍数缩放（如 50%、100%、200%）。
3. 在页面上框选一块区域截图：
   - 初始版本：观察蓝色截图框与鼠标拖拽路径、截图图片内容之间的位置关系。
   - 修正偏移后：框选一条较高的区域，观察截图图片上下是否完整。
4. 进入截图问答模式：
   - 仅轻轻点击或微小拖动，观察是否弹出截图问答对话框。

## 用户体验
- 截图蓝框和实际截图内容不一致，用户难以精确选定想要提问的区域。
- 框选大区域时，截图内容缺失更多，用户误以为系统“少截了”内容。
- 在截图问答模式下，偶然点击也会触发截图弹窗，打断阅读，并造成“误操作”的体验。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：
    - PDF 页面渲染、缩放逻辑。
    - 截图框 `screenshotRect` 的坐标计算与截图裁剪实现。
  - `imates-web/src/views/PdfViewerView.vue`：
    - 接收 `PdfPage` 的 `screenshot-captured` 事件，打开截图问答对话框。
  - `imates-web/src/components/ScreenshotInputDialog.vue`：
    - 截图问答对话框展示截图及输入问题的 UI，原本包含二次裁剪（框选模式）逻辑。
- **涉及模块**：
  - PDF 查看与缩放模块：负责 PDF 渲染及 `transform: scale` 缩放。
  - 截图问答模块：负责将截图与文本问题发送给 AI 进行解答。

## 技术原因 (❌)
1. **截图框与缩放坐标体系混用导致偏移**：
   - 页面主体 `.viewer-inner` 使用 `transform: scale(store.scale)` 对每一页 `.page` 及其子元素进行统一缩放。
   - 截图框 `screenshotRect` 初始使用的是 `pageEl.getBoundingClientRect()` 得到的**已缩放后的视觉坐标**，直接用于 overlay 的 `left/top`。
   - 由于 `.page` 本身再次被整体 `scale`，导致截图框位置等效于被“二次缩放”：
     ```typescript
     const rect = pageEl.getBoundingClientRect()
     const x = event.clientX - rect.left
     const y = event.clientY - rect.top
     screenshotRect.value = { x1: x, y1: y, x2: x, y2: y }
     // getScreenshotRectStyle 中直接使用 x1/y1 作为 CSS 坐标
     ```
   - 结果是：
     - 缩小时（scale < 1）蓝框偏向左上；
     - 放大时（scale > 1）蓝框偏向右下。

2. **裁剪逻辑与坐标换算未统一导致“高度变小”错觉**：
   - 截图裁剪时，初始逻辑使用 canvas client 尺寸推导 DPR，配合 scale 做换算：
     ```typescript
     const clientWidth = pageCanvas.clientWidth || widthCss
     const clientHeight = pageCanvas.clientHeight || heightCss
     const dprX = pageCanvas.width / clientWidth
     const dprY = pageCanvas.height / clientHeight

     const scale = store.scale || 1
     const sx = (x1Css / scale) * dprX
     const sy = (y1Css / scale) * dprY
     const sWidth = (widthCss / scale) * dprX
     const sHeight = (heightCss / scale) * dprY
     ```
   - 在多层缩放（页面 `transform: scale` + canvas 自身尺寸 + 浏览器 DPR）叠加的前提下，这套换算会让人误解为“裁剪少了”。
   - 实际通过日志验证可知：
     - `sHeight ≈ rectHeightCss * (canvasHeight/layoutHeight)`，和图片在弹窗中的 `naturalHeight` 一致；
     - 真正造成“高度变小”的，是 `ScreenshotInputDialog` 容器高度或 `canvas` / `img` 样式的限制（如固定高度、overflow hidden），导致图片显示被裁掉一部分，看起来像“少截了”。

3. **截图问答模式下缺少对“有效拖拽”的过滤**：
   - 截图逻辑仅通过一个较小的尺寸阈值判断是否截图：
     ```typescript
     const widthCss = x2Css - x1Css
     const heightCss = y2Css - y1Css
     if (widthCss <= 5 || heightCss <= 5) {
       return
     }
     ```
   - 当用户轻轻点击或做很小范围拖动时，仍可能超过 5 像素阈值，从而触发截图并弹出问答对话框，造成频繁误触发。

## 正确实现方案 (✅)
1. **统一使用未缩放的页面坐标存储截图框**：
   - 在 pointerDown / pointerMove 中，将视觉坐标除以当前 `scale` 后再存入 `screenshotRect`：
     ```typescript
     const rect = pageEl.getBoundingClientRect()
     const scale = store.scale || 1
     const xVisual = event.clientX - rect.left
     const yVisual = event.clientY - rect.top

     const x = xVisual / scale
     const y = yVisual / scale

     screenshotRect.value = {
       pageIndex,
       x1: x,
       y1: y,
       x2: x,
       y2: y,
     }
     ```
   - `getScreenshotRectStyle` 中直接使用这些未缩放坐标：
     ```typescript
     const x1 = Math.min(rect.x1, rect.x2)
     const y1 = Math.min(rect.y1, rect.y2)
     const x2 = Math.max(rect.x1, rect.x2)
     const y2 = Math.max(rect.y1, rect.y2)

     const width = x2 - x1
     const height = y2 - y1

     return {
       position: 'absolute',
       left: `${x1}px`,
       top: `${y1}px`,
       width: `${width}px`,
       height: `${height}px`,
       boxSizing: 'border-box',
     }
     ```
   - 这样截图框和页面都在“未缩放坐标系”下，由外层 `transform: scale` 统一缩放，不再产生偏移。

2. **裁剪逻辑使用与 layout 一致的 DPR 推导，并确认只是显示问题**：
   - 使用 `layout.width/height` 与 `pageCanvas.width/height` 的比例作为 DPR，确保裁剪区域与 PDF 逻辑尺寸一致：
     ```typescript
     const dprX = pageCanvas.width / layout.width
     const dprY = pageCanvas.height / layout.height

     const sx = x1Css * dprX
     const sy = y1Css * dprY
     const sWidth = widthCss * dprX
     const sHeight = heightCss * dprY
     ```
   - 通过日志比对 `sHeight` 与 `ScreenshotInputDialog` 中图片 `height`，确认裁剪内容本身是完整的，问题在于弹窗里 canvas/img 的展示。

3. **简化 ScreenshotInputDialog，去除二次裁剪逻辑，改为图片预览 + 问题输入**：
   - 模板中仅保留截图预览和输入框：
     ```vue
     <div class="screenshot-preview">
       <div v-if="screenshotDataUrl" class="image-container">
         <img :src="screenshotDataUrl" alt="截图预览" class="preview-image" />
       </div>
     </div>
     ```
   - 删除所有 `cropCanvas`、`cropRect`、蒙版、光标等相关状态和方法，`handleConfirm` 直接使用原始截图：
     ```typescript
     const handleConfirm = async () => {
       if (!questionText.value.trim()) {
         showMessage('请输入要问的问题', 'warning')
         return
       }
       if (!props.screenshotDataUrl) {
         showMessage('截图数据丢失，请重新截图', 'error')
         return
       }

       emit('confirm', questionText.value.trim(), props.screenshotDataUrl)
       localVisible.value = false
     }
     ```
   - CSS 层面：用固定高度 + `max-height: 100%` + `object-fit: contain` 确保整张图片始终完整可见，不被容器裁掉：
     ```scss
     .screenshot-preview {
       flex: 1;
       height: 270px;
       display: flex;
       align-items: center;
       justify-content: center;
       background: #f5f5f5;
       border-radius: 8px;
       border: 1px solid #e0e0e0;
       position: relative;

       .image-container {
         width: 100%;
         height: 100%;
         display: flex;
         align-items: center;
         justify-content: center;
       }

       .preview-image {
         max-width: 100%;
         max-height: 100%;
         object-fit: contain;
         display: block;
       }
     }
     ```

4. **提高截图的最小尺寸阈值，降低误触发概率**：
   - 在 `PdfPage.vue` 的截图结束逻辑中，将最小尺寸从 5 提高到 20 像素：
     ```typescript
     const widthCss = x2Css - x1Css
     const heightCss = y2Css - y1Css
     const minSize = 20
     if (widthCss <= minSize || heightCss <= minSize) {
       return
     }
     ```
   - 如有需要，还可进一步增加“按下到抬起的位移阈值”或时间阈值，但当前项目中仅通过尺寸阈值已显著降低轻触误触发。

## 测试验证
- **测试场景**：
  - 场景1：100% 缩放下截图
    - 步骤：不缩放 PDF，框选小区域与较大区域，检查蓝框与截图图片内容是否完全对齐。
    - 预期：蓝框和截图图片内容边界一致，无偏移；截图图片高度与蓝框视觉高度成比例一致。
  - 场景2：缩放到 50% 和 200% 截图
    - 步骤：分别在 50%、200% 缩放下截取相同内容区域。
    - 预期：每种缩放下蓝框与截图图片内容对齐；不会因缩放产生偏移或高度差异。
  - 场景3：截图问答模式下轻触与正常拖拽
    - 步骤：进入截图模式后，仅轻轻点击或拖动 10 像素左右，再拖动 40 像素以上的明显框选。
    - 预期：小范围触摸不会触发截图；明显框选可以正常弹出截图问答对话框。

- **验证方法**：
  - 使用浏览器开发者工具检查蓝框和截图图片边界是否重合（通过对比像素坐标和视觉边界）。
  - 打印日志确认 `rectHeightCss`、`sHeight`、图片 `naturalHeight` 的比例关系符合预期。
  - 反复测试轻触与短拖动，确认不会再频繁误触截图弹窗。

## 预防措施
- 在涉及多重缩放（CSS transform + canvas + DPR）的场景中，提前设计清晰的“统一坐标系”（如统一以未缩放页面坐标为基准），避免在不同层级混用视觉坐标和逻辑坐标。
- 涉及截图、拖动等交互时，增加最小尺寸和最小位移阈值，过滤掉轻触与抖动产生的误操作。
- 在 UI 层展示截图/预览时，优先采用 `object-fit: contain` + 可滚动容器，而不是固定高度 + overflow hidden，避免给人“截少内容”的错觉。
- 复杂交互组件（如二次裁剪工具）建议独立封装，避免与主功能（PDF 截图）高度耦合，以便出问题时可以快速降级或替换。

## 可复用经验
- 在包含缩放的绘制/截图场景中，优先将所有逻辑坐标统一在“未缩放空间”，最终交由单一 `transform: scale` 控制视觉缩放，避免多点缩放叠加带来的误差和难以追踪的问题。
- 截图、框选这类交互，前期可以从“简单版”开始（整图截图 + 预览 + 提问），在确认主链路稳定后，再考虑增加二次裁剪等高级功能，否则会显著放大排查成本。
- 当用户反馈“内容少了/高度不对”时，不仅要检查计算逻辑，也要检查展示容器是否对图片做了二次裁剪或缩放；善用 `naturalWidth/naturalHeight` 和日志比对，可以快速分辨是裁剪问题还是展示问题。
