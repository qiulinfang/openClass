问题序号：1：老师通话前端消息处理链路缺失说明

## 问题元信息
- **问题分类**：后端
- **严重程度**：中
- **影响范围**：老师通话、音视频信令和房间管理功能
- **发现日期**：2025-12-08
- **解决状态**：已解决

## 问题现象
老师通话过程中，前端发送的 offer/answer/candidate 等消息如何被后端接收、鉴权、转发缺少统一说明，导致排查通话问题时无法快速定位消息路径。

## 复现步骤
1. 发起老师与学生通话。
2. 观察前端日志可看到 WebSocket/HTTP 请求，但后端缺少对应说明。
3. 遇到通话失败时，很难依据文档定位消息在后端的处理节点。

## 用户体验
- 影响点1：通话建立失败时排查成本高。
- 影响点2：消息链路不清晰导致误判前端或后端问题。
- 影响点3：新成员难以理解通话房间状态管理。

## 相关文件/模块
- **涉及文件**：
  - `imates-service/service/**`：通话控制器与 WebSocket 入口（需进一步梳理）。
- **涉及模块**：
  - 通话控制模块：处理发起、挂断、房间状态。
  - 信令转发模块：负责 offer/answer/candidate 的鉴权与转发。

## 技术原因 (❌)
1. 原因1：缺少统一的通话消息路由说明。
2. 原因2：房间状态缓存与鉴权逻辑未文档化。
3. 原因3：信令控制类分散，难以整体理解。

```java
// ❌ 示例：缺乏鉴权与状态路由，接口只能简单转发
@PostMapping("/call/signal")
public void handleSignal(@RequestBody SignalDTO dto) {
    webSocketTemplate.convertAndSend(dto.getTarget(), dto);
}
```

## 正确实现方案 (✅)
1. 方案1：将通话消息分层——入口鉴权、业务路由、状态更新、消息分发。
2. 方案2：在 WebSocket 处理器中补充房间状态校验与错误返回。
3. 方案3：更新 doc/api-overview.md，记录每类消息的处理顺序。

```java
// ✅ 示例：统一鉴权与房间状态更新，再转发
@PostMapping("/call/signal")
public R<Void> handleSignal(@RequestBody SignalDTO dto) {
    authService.checkUser(dto.getSenderId(), dto.getRoomId());
    roomService.ensureActive(dto.getRoomId());
    signalRouter.route(dto);
    signalBroadcaster.forward(dto);
    return R.ok();
}
```

## 关键代码/公式
- 代码片段1：`signalRouter.route(dto)` —— 根据 type(OFFER/ANSWER/CANDIDATE) 分发到对应处理器。
- 代码片段2：`signalBroadcaster.forward(dto)` —— 查找房间内在线成员并推送信令。
- 公式/算法：房间状态机 `CALLING -> RINGING -> IN_CALL -> ENDED`。

## 测试验证
- **测试场景**：
  - 场景1：学生发起通话→老师接听→通话正常建立，验证消息链路。
  - 场景2：老师拒绝通话，验证状态回滚与提示。
- **验证方法**：
  - 方法1：抓取 WebSocket 与后台日志，确保每类消息都有对应处理记录。
  - 方法2：模拟异常请求，确认鉴权失败能在入口被拒绝。

## 预防措施
- 措施1：为信令消息建立统一文档。
- 措施2：在代码中加入结构化日志输出房间与消息状态。
- 措施3：新增通话链路巡检脚本，定期验证。
