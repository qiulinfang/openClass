问题序号：登录页面userid取值来源不清问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`低`
- **影响范围**：`登录页账号回填/自动登录排查`
- **发现日期**：`2025-12-26`
- **解决状态**：`已解决`

## 问题现象
排查登录页“userid/账号”来源时，容易误以为来自 `CURRENT_USER_ID` 或 `studentUserId` 等“当前用户/研伴学生ID”，导致在联调/排障时对“登录页回填的账号”理解不一致。

## 复现步骤
1. 步骤1：打开 Web 登录页 `#/login`。
2. 步骤2：观察账号输入框自动回填的内容。
3. 步骤3：在开发者工具查看 `localStorage`，发现回填值来自 `localStorage['userId']`，而非 `CURRENT_USER_ID`/`studentUserId`。

## 用户体验
- 登录页账号回填来源不清晰，排障成本高。
- 误用 `CURRENT_USER_ID`/`studentUserId` 作为“登录页账号”，可能导致问题定位方向错误。
- 在学伴/研伴多套登录态并存时，容易产生“账号串了”的误解。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/views/LoginView.vue`：登录页回填逻辑调用 `getUserId()/getPassword()`。
  - `imates-web/src/services/http/auth-service.ts`：`getUserId()` 实际读取 `localStorage['userId']`；`loginXueban()` 写入 `userId/userPassword`。
- **涉及模块**：
  - 认证模块：账号/密码持久化与回填。

## 技术原因 (❌)
1. 登录体系中同时存在多种“ID”概念（`userId`、`CURRENT_USER_ID`、`studentUserId`），命名接近且存储位置都在 `localStorage`，容易混淆。
2. 登录页回填逻辑只依赖 `getUserId()`，但未在页面层明确说明其来源与含义。
3. `getCurrentYanbanUserId()` 等方法会回退读取 `studentUserId`，进一步加重“userid到底是哪一个”的认知负担。

❌ 错误理解示例（把登录页回填账号当成当前会话用户ID）：
```typescript
// 错误示例：以为登录页账号应从 CURRENT_USER_ID 读取
const account = localStorage.getItem('CURRENT_USER_ID')
```

## 正确实现方案 (✅)
1. 明确登录页账号回填的真实来源：`LoginView` 调用 `getUserId()`，而 `getUserId()` 读取 `localStorage['userId']`（即上一次学伴登录时保存的账号）。
2. 明确写入时机：`loginXueban(account, password)` 成功后写入 `localStorage['userId']` 与 `localStorage['userPassword']`。
3. （可选）若后续需要消除混淆：
   - 统一命名（例如把 `userId` 改为 `lastLoginAccount` 这类语义更明确的 key），或
   - 在认证模块集中定义并导出所有 `localStorage key` 常量，避免散落与误用。

✅ 正确理解/用法示例：
```typescript
// LoginView.vue 中：回填账号密码
const savedUserId = getUserId()
const savedPassword = getPassword()

if (savedUserId && savedPassword) {
  loginForm.account = savedUserId
  loginForm.password = savedPassword
}
```

## 关键代码/公式
- 代码片段1：登录页回填逻辑（`LoginView.vue`）
```typescript
// imates-web/src/views/LoginView.vue
const savedUserId = getUserId()
const savedPassword = getPassword()

if (
  savedUserId &&
  savedPassword &&
  savedUserId !== 'undefined' &&
  savedPassword !== 'undefined' &&
  savedUserId.trim() !== '' &&
  savedPassword.trim() !== ''
) {
  loginForm.account = savedUserId
  loginForm.password = savedPassword
}
```

- 代码片段2：`getUserId()` 的真实读取来源（`auth-service.ts`）
```typescript
// imates-web/src/services/http/auth-service.ts
export const getUserId = (): string | null => sanitize(localStorage.getItem('userId'))
export const getPassword = (): string | null => sanitize(localStorage.getItem('userPassword'))
```

- 代码片段3：写入来源（`loginXueban` 成功后写入）
```typescript
// imates-web/src/services/http/auth-service.ts
localStorage.setItem('XUEBAN_TOKEN', token)
localStorage.setItem('userId', account)
localStorage.setItem('userPassword', password)
localStorage.setItem('lastLoginTime', Date.now().toString())
```

## 测试验证
- **测试场景**：
  - 场景1：清空 `localStorage['userId']` 与 `localStorage['userPassword']`，刷新登录页，账号密码不应自动回填。
  - 场景2：完成一次 `loginXueban` 登录后刷新登录页，账号密码应从 `localStorage['userId']/'userPassword'` 自动回填。
  - 场景3：仅存在 `studentUserId`（研伴登录态）但不存在 `userId` 时，登录页账号不应被 `studentUserId` 回填。
- **验证方法**：
  - 方法1：在浏览器 DevTools -> Application -> Local Storage 查看 `userId/userPassword` 是否存在且与回填一致。
  - 方法2：在登录页输入框中观察 `loginForm.account/loginForm.password` 的初始值。

## 预防措施
- 在项目内建立“账号/用户ID/登录态 key”规范表（含语义、写入时机、读取方）。
- 尽量避免模糊命名（`userId` 这种在多系统场景下语义不够清晰）。
- 对关键认证信息的存储与回填增加单元/集成测试覆盖（至少覆盖 key 存在/不存在/为 `undefined` 字符串等边界）。

## 可复用经验
- 多系统（学伴/研伴）共存时，必须区分“账号(登录凭据)”“当前用户ID(会话主体)”“业务侧用户ID(学生ID等)”三类概念。
- `localStorage` key 建议集中管理并使用语义化命名，减少跨模块误用。
