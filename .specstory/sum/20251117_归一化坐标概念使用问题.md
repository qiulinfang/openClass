问题序号：归一化坐标概念使用问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：中
- **影响范围**：涉及坐标计算的交互功能（PDF 高亮、笔记锚点、绘制等）
- **发现日期**：2025-11-17
- **解决状态**：已解决

## 问题现象
在实现 PDF 阅读器的高亮与笔记功能时，涉及多套坐标体系：
- 屏幕坐标（`clientX/clientY`）
- 页面布局坐标（`layout.width/layout.height`）
- CSS 缩放后的视觉坐标（`transform: scale(...)`）
- MuPDF 的 PDF 页面坐标（`page.getBounds()` 对应的坐标系）

在讨论中，对“归一化坐标”的概念和作用容易混淆：
- 一开始在点击添加笔记锚点时，直接用 `pixel / layout` 得到一个数值，却没有明确这是“比例坐标（0~1）”，容易误以为仍然是像素。
- 当引入 CSS `scale` 后，如果没有清晰区分“归一化前”和“归一化后”的坐标含义，极易导致位置偏移问题（此前的锚点偏移问题就是典型后果）。

## 复现步骤
本问题本身是概念性问题，不是具体 bug，但可以通过以下场景感受到混淆风险：
1. 对 PDF 页面进行缩放（通过 CSS `transform: scale`）。
2. 在缩放后继续使用之前的逻辑计算 `x = (clientX - rect.left) / layout.width`。
3. 未意识到 `x` 实际上已经是“被缩放的像素 / 未缩放 layout”，会被当作“正常归一化坐标”使用。
4. 渲染时再用 `x * layout.width` + CSS scale，就会产生偏移，而问题根源是“归一化概念未搞清楚”。

## 用户体验
- 影响点1：开发者在调试时难以快速定位坐标偏移的真正原因（以为是渲染问题，实际是归一化定义错误）。
- 影响点2：后续继续扩展高亮、绘制、选择等功能时，如果对归一化坐标理解不清晰，容易反复踩坑。
- 影响点3：团队成员阅读代码时，如果注释和命名没有明确“归一化”的含义，会增加理解成本和出错概率。

- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：包含锚点笔记、手写高亮、缩放与坐标转换逻辑。
- **涉及模块**：

## 技术原因 (❌)
1. **归一化坐标概念未明确区分**：
   - 归一化坐标本质上是“相对于宽高的比例值（0~1）”，而非像素。
   - 如果开发者忽略了这一点，容易在不同坐标系之间做运算时产生错误（例如拿已经被 scale 处理过的像素去除以未缩放宽度）。

2. **未统一“坐标系 → 归一化 → 坐标系”的转换流程**：
   - 点击时的坐标从 `clientX/clientY` 经过多步转换，却没有一条清晰的链路说明：Screen → Page → Normalized → PDF。
   - 渲染时也同样需要反向转换：Normalized → Page → Screen，但如果概念不清晰，很容易在中间某一步漏掉 scale 或 layout。

3. **命名与注释不够“概念化”**：
   - 变量名 `x/y` 容易被误解为“像素”，而不是“比例”；
   - 如果注释没点明“这是归一化后的 0~1 坐标”，阅读者不容易意识到这点，从而错误使用。

**示例代码（容易引发误解的写法） (❌)：**
```ts
// 点击页面添加笔记（旧逻辑示意）
const handlePageClick = (
  event: MouseEvent,
  pageIndex: number,
  layout: { width: number; height: number },
) => {
  const target = event.currentTarget as HTMLElement
  const rect = target.getBoundingClientRect()

  // 这里直接除以 layout.width/layout.height
  // 如果没意识到这是“比例坐标”，后续处理很容易当成像素来用
  const x = (event.clientX - rect.left) / layout.width
  const y = (event.clientY - rect.top) / layout.height

  pendingNotePosition.value = { pageIndex, x, y }
}
```

## 正确实现方案 (✅)
1. **明确归一化坐标的定义**：
   - 归一化坐标 = `相对位置比例`，取值范围 `[0,1]`；
   - 计算方式：`normalizedX = (未缩放像素X) / pageWidth`，`normalizedY = (未缩放像素Y) / pageHeight`；
   - 使用时：`pixelX = normalizedX * pageWidth`，`pixelY = normalizedY * pageHeight`。

2. **统一坐标转换链路并写清楚**：
   - 点击时（Screen → Page → Normalized）：
     1. 从 `clientX/clientY` 减去 `rect.left/top` 得到“视觉局部坐标”；
     2. 除以当前 CSS `scale` 得到“未缩放页面坐标”；
     3. 再除以 `layout.width/height` 得到归一化比例（0~1）。

   - 渲染时（Normalized → Page → Screen）：
     1. 用归一化比例乘以当前页的 `layout.width/height` 得到“未缩放页面坐标”；
     2. 再乘以 CSS `scale` 得到最终视觉坐标。

3. **在代码与注释中显式标注“归一化坐标”含义**：
   - 在定义和使用归一化坐标的位置添加明确注释，例如：`// 归一化坐标 [0,1]`。
   - 对转换函数做清晰命名（如 `screenPointToPdfPoint`、`pdfPointToScreenPoint`），避免混用。

**正确示例代码 (✅)：**
```ts
// 点击页面添加笔记（含归一化说明）
const handlePageClick = (
  event: MouseEvent,
  pageIndex: number,
  layout: { width: number; height: number },
) => {
  if (isHighlightMode.value) return
  if (!isAddingNote.value) return

  const target = event.currentTarget as HTMLElement
  const rect = target.getBoundingClientRect()

  // 当前视觉缩放比例（由 CSS transform: scale 控制）
  const scale = store.scale || 1

  // 1. 视觉坐标（缩放后）
  const localXVisual = event.clientX - rect.left
  const localYVisual = event.clientY - rect.top

  // 2. 折算为未缩放页面坐标
  const localX = localXVisual / scale
  const localY = localYVisual / scale

  // 3. 归一化到 [0,1]（归一化坐标）
  const x = localX / layout.width   // 0~1
  const y = localY / layout.height  // 0~1

  if (x < 0 || x > 1 || y < 0 || y > 1) return

  // 保存归一化坐标，后续与缩放、分辨率无关
  pendingNotePosition.value = { pageIndex, x, y }
}

// 渲染锚点：Normalized -> Page
const getNoteStyle = (note: PageNote, layout: { width: number; height: number }): CSSProperties => ({
  position: 'absolute',
  left: `${note.x * layout.width}px`,
  top: `${note.y * layout.height}px`,
})
```

## 关键代码/公式
- **归一化公式**：
  ```ts
  normalizedX = localX / pageWidth   // 0 <= normalizedX <= 1
  normalizedY = localY / pageHeight  // 0 <= normalizedY <= 1
  ```

- **还原像素坐标公式**：
  ```ts
  localX = normalizedX * pageWidth
  localY = normalizedY * pageHeight
  ```

- **考虑 CSS scale 时的坐标关系**：
  ```ts
  // 从 Screen (视觉) 到未缩放 Page
  localX = (clientX - rect.left) / scale
  localY = (clientY - rect.top) / scale

  // 从归一化回到视觉坐标
  const localX = normalizedX * pageWidth
  const localY = normalizedY * pageHeight
  const visualX = localX * scale
  const visualY = localY * scale
  ```

## 测试验证
- **测试场景**：
  - 场景1：缩放比例为 1
    - 步骤：点击页面任意位置添加笔记，确认 `x/y` 在 0~1 范围，锚点位置正确。
  - 场景2：缩放比例为 2 或 3
    - 步骤：重复在多个位置添加笔记，观察锚点是否仍精准对齐点击位置。
  - 场景3：不同窗口尺寸 / 不同设备
    - 步骤：在不同分辨率下进行相同操作，确认归一化坐标的使用不会受屏幕尺寸影响。

- **验证方法**：
  - 方法1：在控制台打印 `localX/localY` 与 `x/y` 的数值，验证归一化是否在 0~1 内且随点击位置变化合理。
  - 方法2：切换不同的 `scale` 值，比较锚点是否始终对齐点击点。

## 预防措施
- 措施1：在设计阶段先画出“坐标转换链路图”，明确每一步的坐标系和单位含义。
- 措施2：为所有与坐标相关的变量和函数添加明确命名和注释（如 `normalizedX`、`pdfPoint`），避免使用过于模糊的 `x/y`。
- 措施3：在代码评审中，重点关注涉及缩放、坐标转换的逻辑，确保归一化的使用一致、正确。

## 可复用经验
- 经验1：在多坐标系（Screen/Page/PDF）场景中，**优先使用归一化坐标存储逻辑位置**，渲染时再根据当前环境还原为像素坐标。
- 经验2：当涉及缩放（CSS transform 或 Canvas scale）时，点击/绘制类功能几乎一定需要显式考虑 scale，否则坐标很难对得齐。
- 经验3：对“归一化坐标”这一概念做团队级约定（命名规范、注释模版），能显著减少后续在地图、PDF、画布等场景中的重复踩坑。
