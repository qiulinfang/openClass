问题序号：02：IM多实例部署无法跨实例直推消息问题

## 问题元信息
- **问题分类**：`架构`
- **严重程度**：`中`
- **影响范围**：`service-im-wss 多实例部署、客服/用户分布式连接、消息投递可靠性`
- **发现日期**：`2025-12-26`
- **解决状态**：`待解决`

## 问题现象
- 单实例部署时：用户发给固定客服 `Agent_007` 能正常收到。
- 多实例部署时：用户可能连到实例 A，客服连到实例 B，用户发送后客服收不到（或发送方只收到 OFFLINE）。

## 复现步骤
1. 步骤1：同时启动 2 个 `service-im-wss` 实例（A/B）。
2. 步骤2：让用户连接到实例 A，让客服连接到实例 B（通过负载均衡或手工控制）。
3. 步骤3：用户发送 `CHAT`，观察客服实例无法收到 PUSH。

## 用户体验
- 消息“发出但对方收不到”，用户会误以为系统故障。
- 客服端漏消息，影响响应效率。
- 多实例上线后问题放大，定位困难。

## 相关文件/模块
- **涉及文件**：
  - `service/service-im-wss/src/main/java/com/blw/edu/service/im/ws/SessionRegistry.java`：本机 session 映射
  - `service/service-im-wss/src/main/java/com/blw/edu/service/im/redis/OnlineRegistry.java`：Redis 在线注册
  - `service/service-im-wss/src/main/java/com/blw/edu/service/im/ws/ImWebSocketHandler.java`：消息路由
  - `service/service-im-wss/src/main/java/com/blw/edu/service/im/port/ImMessagePublishPort.java`：发布扩展点（当前 Noop）
- **涉及模块**：
  - IM WebSocket 服务
  - Redis
  -（未来）MQ/消息总线

## 技术原因 (❌)
1. 原因1：`SessionRegistry` 为内存结构，只能拿到本实例内的 `WebSocketSession`。
2. 原因2：当前代码未实现“跨实例投递”（例如 MQ/Redis PubSub/HTTP 转发）。
3. 原因3：Redis 在线注册目前主要用于“在线标记”，未携带/未利用 `instanceId` 做定向投递。

（问题代码示意）
```java
// ❌ 仅能本机直推
WebSocketSession agentSession = sessionRegistry.getAgentSession(agentId);
if (agentSession != null && agentSession.isOpen()) {
  sendJson(agentSession, push);
} else {
  // 多实例时，即使 agent 在线但在别的实例，这里也拿不到 session
}
```

## 正确实现方案 (✅)
1. 方案1：Redis 在线 value 保存 `instanceId + sessionId`（或 JSON），用于判断目标在哪个实例。
2. 方案2：实现 `ImMessagePublishPort` 的 MQ 发布版本（例如 RabbitMQ），跨实例投递 `ImChatEvent`。
3. 方案3：各实例订阅同一 topic/queue，收到事件后在本机查 session 并 PUSH。

（正确方案伪代码）
```java
// ✅ A实例：收到消息后
if (agentSessionLocal == null) {
  publishPort.publish(event); // MQ
}

// ✅ B实例：消费 MQ 后
onEvent(event):
  sess = sessionRegistry.getAgentSession(event.toId)
  if sess open: sendJson(sess, push)
```

## 关键代码/公式
- **关键设计点**：
  - `onlineKey -> {instanceId, sessionId}`
  - `event` 通过 MQ 在实例间转运

## 测试验证
- **测试场景**：
  - 场景1：用户连实例 A，客服连实例 B，发送消息应能到达。
  - 场景2：实例 B 下线，消息应回执为离线或进入重试/存储队列。
- **验证方法**：
  - 方法1：在 MQ 消费日志中观察到 event 从 A 到 B。
  - 方法2：客服端能收到 PUSH，且 `SEND_STATUS` 能体现真实投递状态。

## 预防措施
- 措施1：上线前明确单实例与多实例的能力边界（文档/开关）。
- 措施2：将“跨实例投递”作为 IM 上线多实例的硬前置条件。
- 措施3：为分布式投递增加链路追踪字段（messageId/traceId）。

## 可复用经验
- 经验1：WebSocket 推送的“直推能力”天然是本机内存能力，多实例必须补上消息总线。
- 经验2：Presence（在线标记）与 Delivery（投递）是两件事，presence 不能替代投递链路。
- 经验3：先预留 Port/Adapter 扩展点（Noop -> MQ）能降低后续改造成本。
