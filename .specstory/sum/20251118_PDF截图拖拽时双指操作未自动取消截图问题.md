问题序号：PDF 截图拖拽时双指操作未自动取消截图问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`中`
- **影响范围**：`PDF 浏览页截图功能，触控设备用户`
- **发现日期**：`2025-11-18`
- **解决状态**：`已解决`

## 问题现象
在 PDF 浏览页面开启截图模式时：
- 用户用 **单指** 在页面上拖动可以拉出一个截图选框；
- 截图完成后会生成对应区域的图片并弹出对话框。

但是，在截图拖拽过程中：
- 如果用户中途 **再放下一根手指**（变成双指），
- 然后松开手指，原先的截图拖拽流程仍然会在 `pointerup` 结束时生成截图，
- 导致用户实际做了一个“截图 + 多指缩放/调整”的混合手势，却依然得到了一个不期望的截图结果。

## 复现步骤
1. 进入 PDF 浏览页面，打开截图工具（`screenshot` 模式）。
2. 使用单指在页面上拖出一个截图框：
   - 观察屏幕上出现半透明矩形区域，`isDraggingScreenshot = true`。
3. 在不抬起第一根手指的情况下，再放下第二根手指到屏幕上：
   - 形成短暂的双指状态。
4. 依次松开手指。
5. 观察：
   - 仍然会触发一次截图裁剪并弹出截图输入对话框，
   - 但此时用户预期是“取消截图，进行缩放/拖动”，不是保留截图。

## 用户体验
- 影响点1：用户想中途放弃截图、改为缩放或拖动，但系统仍然生成了一张截图，造成“误截图”。
- 影响点2：需要手动关闭截图对话框或删除这个不需要的截图，增加操作成本。
- 影响点3：在课堂或演示场景中，误截图会打断讲解流程，影响节奏和注意力。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：
    - 实现截图模式逻辑（矩形选区的开始/拖动/结束），以及 touch/pointer 多指手势处理。
- **涉及模块**：
  - 截图功能模块：
    - `isScreenshotMode`、`screenshotRect`、`isDraggingScreenshot` 等状态；
    - 截图裁剪并通过 `emit('screenshot-captured', blob)` 向上层发送图片。
  - 触摸手势模块：
    - `handleTouchStart/Move/End` 与 `handleHighlightPointerDown/Move/Up` 的交互协调。

## 技术原因 (❌)
1. 截图拖拽与多指手势之间缺少“中途取消机制”：
   - 截图开始时仅依赖 `pointer` 事件和 `isScreenshotMode` 状态拉出矩形；
   - 在拖拽过程中，如果出现第二个触点，没有立刻清理 `screenshotRect` 和 `isDraggingScreenshot`。
2. 截图结束逻辑只判断截图矩形尺寸是否满足阈值：
   - 在 `handleHighlightPointerUp` 中，只要 `screenshotRect` 仍然存在且宽高大于最小值，就会进行裁剪并发出截图；
   - 没有意识到“拖拽过程中曾经出现多指”这一语义，不能区分“有效截图”和“被中断的截图”。
3. touch 层虽然有双指缩放/拖动逻辑，但没有反向通知截图模块：
   - `TouchEvent` 的 `touches.length` 变化没有用于控制截图状态，
   - 导致截图模块把一次“被双指中断的拖拽”当成正常完成的单指截图来处理。

### 错误代码示例 (片段)
❌ 截图结束时只依据矩形尺寸判断，而没有考虑拖拽是否被多指中断：
```ts
// 截图模式：结束拖拽，裁剪截图
if (
  isScreenshotMode.value &&
  isDraggingScreenshot.value &&
  screenshotRect.value &&
  screenshotRect.value.pageIndex === pageIndex
) {
  isDraggingScreenshot.value = false

  const rectInfo = screenshotRect.value
  screenshotRect.value = null

  const x1Css = Math.min(rectInfo.x1, rectInfo.x2)
  const y1Css = Math.min(rectInfo.y1, rectInfo.y2)
  const x2Css = Math.max(rectInfo.x1, rectInfo.x2)
  const y2Css = Math.max(rectInfo.y1, rectInfo.y2)

  const widthCss = x2Css - x1Css
  const heightCss = y2Css - y1Css
  if (widthCss <= 5 || heightCss <= 5) {
    return
  }
  // ... 继续执行截图裁剪并 emit
}
```

## 正确实现方案 (✅)
1. 在截图拖拽过程中监控 touch 层的触点数量：
   - 在 `handleTouchStart` 中，如果当前处于 `isScreenshotMode` 且 `event.touches.length >= 2`：
     - 若 `isDraggingScreenshot` 为 `true` 且 `screenshotRect` 不为空，
     - 立即将其视为“截图被中断”，直接取消本次截图状态：
       - `isDraggingScreenshot.value = false`
       - `screenshotRect.value = null`
2. 将“截图被中断”的语义设计成一个简单规则：
   - 一旦多指出现，就等价于“放弃本次截图”；
   - 后续 `pointerup` 虽然仍可能触发，但因为截图状态已经被清空，不会再执行裁剪和 `emit`。
3. 保持现有多指缩放/拖动逻辑不变，只是让多指触发时额外通知截图模块取消当前截图。

### 正确代码示例 (片段)
✅ 在 `handleTouchStart` 中，检测到截图拖拽 + 多指时立刻取消截图：
```ts
// 触摸开始（双指）
const handleTouchStart = (event: TouchEvent) => {
  if (isScreenshotMode.value && event.touches.length === 1) {
    event.preventDefault()
    return
  }
  // 高亮、画笔或橡皮擦模式下，优先将触摸事件用于绘制，避免触发浏览器滚动/缩放手势
  if (['highlighter', 'pen', 'eraser-draw'].includes(currentMode.value)) {
    event.preventDefault()
  }
  if (!containerRef.value || !viewerContainer.value) return

  // 截图拖拽过程中一旦检测到多指，立即取消当前截图框
  if (isScreenshotMode.value && event.touches.length >= 2) {
    if (isDraggingScreenshot.value && screenshotRect.value) {
      isDraggingScreenshot.value = false
      screenshotRect.value = null
    }
  }

  if (event.touches.length === 2) {
    // 多指开始：临时切换为 hand 模式并暂停绘图工具
    if (!isPointerToolSuspended.value) {
      lastToolMode = currentMode.value
      isPointerToolSuspended.value = true
      if (currentMode.value !== 'hand') {
        currentMode.value = 'hand'
      }
    }
    isZooming.value = true
    event.preventDefault()
    // ... 原有捏合初始化
  }
}
```

✅ 截图结束逻辑保持不变，但由于拖拽被多指立即清空状态，因此不会再误发截图：
```ts
// 触摸结束中的截图逻辑保持原样：
// 若 isDraggingScreenshot 已在多指时被置为 false，且 screenshotRect 设为 null，
// 则 handleHighlightPointerUp 中的截图分支不会再进入裁剪流程。
```

## 关键代码/公式
- **关键状态变量**：
  - `isScreenshotMode: Ref<boolean>`：是否处于截图模式。
  - `isDraggingScreenshot: Ref<boolean>`：当前是否正在拖拽截图矩形。
  - `screenshotRect: Ref<ScreenshotRect | null>`：截图矩形的页内逻辑坐标。
- **关键逻辑条件**：
  - `event.touches.length >= 2`：判定当前为多指触控；
  - `isScreenshotMode && isDraggingScreenshot && screenshotRect != null`：判定当前存在一笔进行中的截图拖拽。

## 测试验证
- **测试场景**：
  - 场景1：
    - 开启截图模式 → 单指拖出一个矩形 → 中途放下第二根手指 → 松开所有手指；
    - 预期：矩形在多指出现时立即消失，最后 **不** 弹出截图对话框。
  - 场景2：
    - 开启截图模式 → 单指完整拉出截图 → 松手；
    - 预期：正常生成截图并弹出输入对话框，行为不受多指逻辑影响。
  - 场景3：
    - 开启截图模式 → 直接双指接触屏幕，不进行单指拖拽；
    - 预期：不会生成截图，也不会留下任何选框。

- **验证方法**：
  - 方法1：在平板或触控屏上多次执行上述场景，观察是否还有“误截图”出现。
  - 方法2：通过在控制台打印关键状态（`isDraggingScreenshot`、`screenshotRect`）验证：
    - 多指出现的瞬间，这两个状态已被清空。

## 预防措施
- 措施1：对类似“拖拽 + 模式切换/多指中断”的交互，统一设计“中途取消”的状态机逻辑，避免依赖单一结束事件。
- 措施2：在涉及截图、录制等“结果型操作”时，尽量增加明确的中断条件（例如：模式切换、多指、窗口失焦），降低误触发概率。
- 措施3：为复杂触控交互补充专门的真机测试用例，覆盖单指、多指、快速切换等边界场景。

## 可复用经验
- 经验1：对于“拖拽 + 结果确认”的功能（截图、选区、高亮等），要明确“放弃条件”，如多指、ESC、模式切换等。
- 经验2：在统一的 touch 入口处集中管理交互模式状态（截图、绘图、缩放、拖动），能显著减少不同模块之间的冲突。
- 经验3：在多指场景下，优先保证“视图控制”（缩放/拖动）的体验，再通过清晰规则让工具操作（绘图/截图）自动让路。
