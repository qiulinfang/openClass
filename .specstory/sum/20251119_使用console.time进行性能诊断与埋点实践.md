问题序号：使用console.time进行性能诊断与埋点实践

## 问题元信息
- **问题分类**：`性能`
- **严重程度**：`低`
- **影响范围**：`前端性能分析与调试流程`
- **发现日期**：`2025-11-19`
- **解决状态**：`已解决`

## 问题现象
- 需要在 Android WebView 中精确定位 PDF 加载与 LearningView 弹窗的卡顿位置，初始代码缺乏系统性的性能日志。
- 对如何在日志中打印时间、如何合理使用 `console.time` / `console.timeEnd`、以及 Chrome/Chromium 支持情况存在疑问。

## 复现步骤
1. 在 WebView 或桌面浏览器中打开包含 PDF 和 LearningView 的页面。
2. 观察首次进入 PDF 页面或弹出 LearningView 弹窗时的卡顿现象。
3. 在缺少埋点的情况下，很难判断是数据加载、布局计算还是渲染过程的具体哪一步最耗时。

## 用户体验
- 影响点1：没有清晰的性能数据，开发者只能凭感觉调试，效率低下。
- 影响点2：无法在多端（桌面、WebView）对比性能瓶颈，优化难度大。
- 影响点3：难以形成可复用的性能诊断套路，后续类似问题会重复踩坑。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：为 PDF 加载、布局、渲染阶段增加 `console.time` 埋点。
  - `imates-web/src/views/LearningView.vue`：为教材信息加载、学习包处理、BScroll 初始化等阶段增加 `console.time` 埋点。
- **涉及模块**：
  - 性能日志与调试工具链（Chrome DevTools、WebView 日志）。

## 技术原因 (❌)
1. 原因1：初始实现中缺少对关键路径（如 PDF 渲染、学习包加载）的系统性时间测量，只能从整体感知“很卡”，无法拆解出具体耗时段。
2. 原因2：对 `console.time` 的使用方式和兼容性不够了解，导致一开始只使用简单 `console.log`，不利于量化分析。
3. 原因3：没有封装统一的“带时间戳的日志”工具函数，埋点风格不统一，分析阅读成本偏高。

❌ 示例：仅使用简单日志，难以量化耗时

```ts
console.log('[PdfPage] loadPdf start')
// ...一大段代码...
console.log('[PdfPage] loadPdf end')
```

## 正确实现方案 (✅)
1. 方案1：在关键函数入口/出口使用 `console.time` / `console.timeEnd`，以统一的标识符标记完整耗时区间（例如 `3.1`、`3.2`、`3.3.5.1` 等）。
2. 方案2：在需要对比局部阶段（如 `openDocument`、布局计算、单页渲染）时，再细化更多埋点，结合堆栈信息定位瓶颈。
3. 方案3：在需要打印精确时间点时，通过 `new Date()` + `toISOString` 或自定义格式输出时间戳，或封装 `logWithTime` 辅助函数。

✅ 示例1：在 `loadPdf` 中对各阶段打点

```ts
// 读取文件为 ArrayBuffer
console.time('3.1')
const arrayBuffer = await file.arrayBuffer()
const uint8Array = new Uint8Array(arrayBuffer)
console.timeEnd('3.1')

// 打开文档
console.time('3.2')
const doc = mupdf.Document.openDocument(uint8Array, 'application/pdf')
console.timeEnd('3.2')

// 渲染整体耗时
console.time('3.3')
await render()
console.timeEnd('3.3')
```

✅ 示例2：在 `render` 中区分布局和渲染阶段

```ts
console.time('3.3.4')
// 计算 pageLayouts、totalHeight、maxWidth
...
await nextTick()
console.timeEnd('3.3.4')

console.time('3.3.5')
// 渲染所有页面（已改为分批）
...
console.timeEnd('3.3.5')
```

✅ 示例3：带时间戳的日志辅助函数

```ts
const logWithTime = (tag: string, extra?: unknown) => {
  const now = new Date()
  const ts = `${now.getHours()}:${now.getMinutes()}:${now.getSeconds()}.${now.getMilliseconds()}`
  if (extra !== undefined) {
    console.log(`[PdfPage] ${tag}`, ts, extra)
  } else {
    console.log(`[PdfPage] ${tag}`, ts)
  }
}

logWithTime('loadPdf start', { name: file.name, size: file.size })
```

## 关键代码/公式
- 代码片段1：分阶段埋点命名规范（示例）

```text
3.1  = file.arrayBuffer
3.2  = mupdf.Document.openDocument
3.3  = render
3.3.1–3.3.4 = render 前置准备（AbortController、countPages、布局计算...）
3.3.5       = 渲染阶段整体
3.3.5.1     = 单页渲染（loadPage → toPixmap → putImageData）
```

- 代码片段2：在 LearningView 中埋点

```ts
onMounted(async () => {
  console.time('学习包加载')
  await loadLearningPackages()
  console.timeEnd('学习包加载')

  console.time('BScroll初始化')
  await initSchemeListBScroll()
  await initResourcesListBScroll()
  console.timeEnd('BScroll初始化')
})
```

## 测试验证
- **测试场景**：
  - 场景1：多次打开 PDF 页面，观察各阶段耗时是否稳定，是否能准确体现优化前后差异。
  - 场景2：多次打开 LearningView 弹窗，在不同教材/章节下对比“学习包加载”、“缩略图检查”的耗时。
- **验证方法**：
  - 方法1：通过控制台查看 `console.time` 的输出，确认埋点名称清晰、一致，方便筛选和比对。
  - 方法2：在优化前后分别采集多组数据，确认特定阶段耗时显著下降（如 `3.3.5` 由 1300ms 降至更低，或分布更均匀）。

## 预防措施
- 措施1：对于重要的性能敏感路径（渲染、IO 密集操作），在开发阶段默认加入 `console.time` 埋点，形成固定套路。
- 措施2：统一埋点命名规范（模块名前缀 + 阶段编号/描述），避免后期难以搜索或混淆。
- 措施3：在 WebView 集成场景中，定期导出性能日志进行分析，避免问题在移动端长期不可见。

## 可复用经验
- 经验1：`console.time` / `console.timeEnd` 在 Chrome 2 及之后版本就已支持，现代 Chromium / WebView 环境中可以放心使用。
- 经验2：对复杂流程分阶段打点（load → layout → render → post-process）是定位性能瓶颈的高性价比方法。
- 经验3：封装简单的 `logWithTime` 工具有助于统一日志格式，提高排查效率。
