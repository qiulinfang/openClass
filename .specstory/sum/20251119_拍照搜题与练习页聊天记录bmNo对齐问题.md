问题序号：拍照搜题与练习页聊天记录bmNo对齐问题

## 问题元信息
- **问题分类**：`[前端/架构]`
- **严重程度**：`[中]`
- **影响范围**：`[拍照搜题页与ExerciseSolve练习页之间的AI题目聊天记录联动]`
- **发现日期**：`2025-11-19`
- **解决状态**：`[已解决]`

## 问题现象
用户在拍照搜题页面针对识别出的题目与 AI 进行对话后，跳转到练习解题页（ExerciseSolveView），选中“看起来是同一题”的题目时，原本在拍照页产生的聊天记录没有出现在练习页中，看起来像“聊天记录丢失”或“不共享”。

## 复现步骤
1. 在拍照搜题页面进行拍照识别，获得题目 A，并在抽屉中的 ChatView 与 AI 聊天若干轮。
2. 完成后，执行“加入练习”等操作，将题目 A 以某种方式加入练习列表。
3. 打开练习解题页 ExerciseSolveView，在题目列表中选中对应的练习题（逻辑上应等同于题目 A）。
4. 切换到“AI引导答题”功能模块，打开 ChatView。
5. 观察聊天记录：之前在拍照页对题目 A 的聊天记录没有出现在练习页。

## 用户体验
- 影响点1：用户认为这是“同一题目”，期望聊天记录在两个入口之间可以共享，却发现记录不见了。
- 影响点2：需要在不同页面重复提问、重复对话，降低学习效率。
- 影响点3：用户对“拍照搜题”和“我的习题”之间的数据打通产生疑惑，认为系统不一致。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/views/PhotoSearchView.vue`：拍照/关键词搜题页面。
  - `imates-web/src/views/ExerciseSolveView.vue`：练习解题页。
  - `imates-web/src/components/ChatView.vue`：通用聊天组件。
  - `imates-web/src/components/chat/strategies/AiExerciseStrategy.ts`：AI题目对话策略。
  - `imates-web/src/stores/aiExerciseChatStore.ts`：AI题目对话的消息存储与历史管理（未在本问题中完全展开）。
- **涉及模块**：
  - 拍照搜题业务模块。
  - 练习题列表与当前题管理模块（questionStore）。
  - AI 题目聊天与历史记录模块。

## 技术原因 (❌)
1. 聊天记录 key 在不同页面来源不一致：
   - 拍照搜题页：ChatView 中的 `currentQuestionId` 一开始可能使用 `question.bmNo || question.id`。
   - 练习页：ChatView 同样使用 `currentQuestion.bmNo || currentQuestion.id`，但 `currentQuestion` 来自 questionStore，可能是另一条记录，`id` 甚至可能完全不同。
2. 拍照题与练习题在数据建模上缺乏**唯一稳定标识**的统一约定：
   - 拍照识别出来的题目对象中包含 `bmNo` 和/或 `id`。
   - 将题目加入练习列表时，后端/前端可能为练习列表中的题重新生成 `id`，导致“逻辑上同一题”在数据上有不同的 `id`。
   - Chat 历史最初部分逻辑将 `id` 作为备选 key 使用，导致“拍照场景里存了一份，以 id 为 key 的历史”，练习页又用另一个 key 查找，最终查不到之前的记录。
3. ChatView 与策略初始化阶段没有强制统一 key 策略：
   - `initializeMessages` 阶段曾使用 `currentQuestion.value?.id || currentQuestion.value?.bmNo` 构造 `currentQuestionId`。
   - AiExerciseStrategy.initialize 只根据传入的 `currentQuestionId` 加载历史，这个值在不同页面构造逻辑不完全一致，造成历史不共享。

## 正确实现方案 (✅)
1. 明确统一的聊天记录 key：使用 `bmNo` 作为题目的稳定唯一标识：
   - 不再使用 `id` 作为 Chat 历史的 key。
   - 要求拍照识别返回结果与练习列表中的这道题都具有相同的 `bmNo`。
2. ChatView 初始化阶段统一使用 `question.bmNo`：
   ```typescript
   const initializeOptions = {
     currentSubject: currentSubject.value as 'biology' | 'math',
     // 统一使用 bmNo 作为聊天记录 key
     currentQuestionId: currentQuestion.value?.bmNo,
     currentQuestionTitle: currentQuestion.value?.question || currentQuestion.value?.title,
     resourceId: props.resourceId,
     hasSelectedQuestion: hasSelectedQuestion.value,
   }
   await chatStrategy.value.initialize(initializeOptions)
   ```
3. 调用 ChatView 时不再单独传 `current-question-id`，而是只传 `question`：
   - 拍照搜题：
     ```vue
     <ChatView
       type="ai-exercise"
       input-mode="simple"
       :compressed-height="97"
       :question="currentQuestionData"
     />
     ```
   - 练习页：
     ```vue
     <ChatView
       v-if="currentFunction === 'chatAi'"
       type="ai-exercise"
       :compressed-height="327"
       :question="currentQuestion"
     />
     ```
   - ChatView 内部统一通过 `currentQuestion.value?.bmNo` 推导出 `currentQuestionId` 传给策略。
4. AiExerciseStrategy.initialize 始终使用 `currentQuestionId`（即 bmNo）加载历史：
   ```typescript
   async initialize(options: InitializeOptions): Promise<void> {
     if (options.hasSelectedQuestion && options.currentQuestionId) {
       const questionId = options.currentQuestionId // 即 bmNo
       await this.aiExerciseStore.loadChatHistory(questionId)
     } else {
       // 无题目时根据需要插入欢迎语
     }
   }
   ```
5. 确保“拍照加入练习”环节不改变 bmNo：
   - 将拍照识别的题目加入练习列表时，应以 bmNo 为题目的稳定标识。
   - 后续在 questionStore 中加载的题目 A，应保持与拍照结果相同的 bmNo，这样在练习页选中该题目时，ChatView 会传入相同的 bmNo 作为聊天 key，自然能共享聊天记录。

## 测试验证
- **测试场景**：
  - 场景1：拍照搜题 → 聊天 → 刷新页面 → 再拍同一题
    - 预期：ChatView 通过相同 bmNo 加载到之前的聊天历史。
  - 场景2：拍照搜题 → 聊天 → 将该题加入练习 → 打开练习页 → 选中该题 → 打开“AI引导答题”
    - 预期：练习页 ChatView 能加载并展示在拍照页产生的聊天记录（前提是拍照题与练习题的 bmNo 对齐）。
  - 场景3：练习页切换不同题目
    - 预期：不同 bmNo 的题目有独立的聊天历史，切换回原题时历史正确恢复。
- **验证方法**：
  - 方法1：在 aiExerciseChatStore 的持久化存储中检查 key：确保只使用 bmNo 作为聊天记录 key。
  - 方法2：通过日志确认 AiExerciseStrategy.initialize 收到的 currentQuestionId 始终为 bmNo，而非混入 id。

## 预防措施
- 措施1：在跨页面共享数据时，优先选用业务上稳定的领域标识（如 bmNo），不要使用实现细节（如数据库自增 id）。
- 措施2：在实现新特性前，设计并文档化“全局唯一 key 策略”，避免后续模块随意选择 key。
- 措施3：对于影响多个入口的功能（如聊天历史共享），编写集成测试覆盖主要用户路径，防止 key 策略变更引发回归问题。

## 可复用经验
- 经验1：跨页面/跨模块共享的数据，一定要有清晰、统一、稳定的业务标识符，并在实现前对齐各个模块的使用方式。
- 经验2：聊天、历史记录、缓存等功能强依赖 key，一旦 key 策略发生变化需要全链路审查，避免局部修改导致行为分叉。
- 经验3：组件与策略解耦时，最好一起审视“上下文传递 + 标识符策略”，避免只改一层导致另一层仍然依赖旧逻辑。
