问题序号：聊天消息字段构造位置说明

## 问题元信息
- **问题分类**：`[后端]`
- **严重程度**：`[中]`
- **影响范围**：`[教师-学生问答系统的消息持久化、调试人员]`
- **发现日期**：`2025-12-12`
- **解决状态**：`[进行中]`

## 问题现象
研发同事需要快速定位 `msgContent/msgReadFlag/msgReadTime/msgSendId/msgSendName/msgSendAvatar/sessionId/createTime` 这些字段的构造位置，但代码分散在 MQ 监听器与服务层中，缺少统一文档，排查成本高。一旦需要新增字段或排查错乱记录，就必须逐一 grep，效率低、容易漏掉关键步骤。

## 复现步骤
1. 在 IDE 中搜索 `msgContent`，会看到同时存在于 `AlcQuestionService` 与 `MessageReceiveListener` 两处构造。
2. 尝试根据变量名追踪时，需要在 Service、MQ、实体等多个文件来回跳转。
3. 无集中说明，导致难以快速确认“老师消息”与“学生消息”分别在哪里写入数据库。

## 用户体验
- 影响点1：后端排查字段异常耗时长。
- 影响点2：缺少统一入口，容易误判字段来源。
- 影响点3：新人接手时难以及时理解消息表的写入流程。

## 相关文件/模块
- **涉及文件**：
  - `app/src/main/java/com/blw/edu/yb/modules/alc/service/AlcQuestionService.java`：老师端保存与推送消息的入口。
  - `app/src/main/java/com/blw/edu/yb/modules/mq/listener/MessageReceiveListener.java`：学生端提问通过 MQ 入库的入口。
  - `app/src/main/java/com/blw/edu/yb/modules/alc/entity/AlcQuestion.java`：消息表实体。
- **涉及模块**：
  - 问答消息服务模块。
  - MQ 消费监听模块。

## 技术原因 (❌)
1. 原因1：Service 与 MQ 监听器各自手动 new `AlcQuestion`，缺少共享的构造工具或注释。
2. 原因2：`msgSendName/msgSendAvatar` 并非直接 set，而是查询历史时联表别名映射，若不了解 SQL，很难从代码中直接看出来源。
3. 原因3：文档缺失，导致“字段从哪来”完全依赖口口相传。

```java
// ❌ 现状：多处散落的字段赋值，缺少说明
AlcQuestion question = new AlcQuestion();
question.setSessionId(req.getSessionId())
        .setMsgSendId(teacherId)
        .setMsgType(req.getMsgType())
        .setMsgContent(req.getMsgContent())
        .setMsgReadFlag(AlcConstant.QUESTION_READ_FLAG_0)
        .setCreateTime(new Date());
```

## 正确实现方案 (✅)
1. 方案1：整理字段构造文档，标注“老师→学生”“学生→老师”各自的入库入口与处理步骤。
2. 方案2：抽象 `QuestionFactory` 或 Builder，收敛字段赋值逻辑，并在方法注释中说明来源。
3. 方案3：在 `historyList` 查询语句旁补充注释，指出 `msgSendName/msgSendAvatar` 由联表别名映射提供。

```java
// ✅ 建议：通过工厂方法集中构造并注释字段来源
public AlcQuestion buildTeacherReply(QuestionReplyReq req, String teacherId) {
    return new AlcQuestion()
            .setSessionId(req.getSessionId())   // 来自请求 sessionId
            .setMsgSendId(teacherId)            // 当前登录老师
            .setMsgType(req.getMsgType())       // 请求指定的消息类型
            .setMsgContent(req.getMsgContent()) // 文本或文件相对路径
            .setMsgReadFlag(AlcConstant.QUESTION_READ_FLAG_0)
            .setCreateTime(new Date());
}
```

## 关键代码/公式
- `AlcQuestionService.replyMessage`：老师端回复时构造消息的唯一入口。
- `MessageReceiveListener.receive`：学生提问经 MQ 入库的唯一入口。
- `AlcQuestionService.historyList`：通过 `ALC_USER.NAME.as("msgSendName")`、`AVATAR.as("msgSendAvatar")` 将用户表字段映射到响应 DTO。

## 测试验证
- **测试场景**：
  - 场景1：老师发送文本，确认数据库 `msgContent` 为原文、`msgSendId` 为老师 ID。
  - 场景2：学生提问上传图片，确认落库后 `msgContent` 为文件相对路径。
  - 场景3：调用历史接口，确认 `msgSendName/msgSendAvatar` 正确返回。
- **验证方法**：
  - 方法1：结合 SQL 日志与数据库记录，核对字段赋值。
  - 方法2：启用断点或日志，确保工厂/文档指向的入口被调用。

## 预防措施
- 措施1：后端字段构造必须抄送到 `/sum` 文档，形成可检索知识库。
- 措施2：为常用实体提供工厂/Builder，避免多处手写赋值。
- 措施3：在 PR Template 中增加“新增字段是否补充文档”的检查项。

- 经验1：涉及多端的公共实体，必须同步整理字段来源。
