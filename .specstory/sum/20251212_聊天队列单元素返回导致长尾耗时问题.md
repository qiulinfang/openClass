问题序号：聊天队列单元素返回导致长尾耗时问题

## 问题元信息
- **问题分类**：`[后端]`
- **严重程度**：`[中]`
- **影响范围**：`[首页聊天 / AI 对话所有用户]`
- **发现日期**：`2025-12-12`
- **解决状态**：`[待解决]`

## 问题现象
聊天接口 `/blw-edu-service-alc/permission/chats` 在 `reason != start` 的轮询阶段，每次请求只 `poll()` 队列中的一个 token，然后立即返回。一次对话往往产生几十个 token，于是前端必须串行发送几十个 HTTP 请求才能拿到完整回答，导致：
- 单次请求耗时约 200~500ms，累计耗时远大于模型真实生成时间。
- 模型早已结束，但后端仍有请求在 `while (response == null)` 中空等，日志时间线被拖长到 15~20 秒。

## 复现步骤
1. 进行首页聊天，抓取浏览器 Network。
2. 观察 `/permission/chats` 请求：返回体每次只有一个极小的 token，如 “你\n”“发\n”。
3. 统计请求数量和总时长，可达几十次、十几秒，明显高于模型 2 秒的生成时间。

## 用户体验
- 对话响应看似“慢吞吞”，即使模型已完成也要等待所有轮询。
- Network 中充满 Pending 或长耗时请求，前端难以判断是真慢还是设计问题。
- 服务器线程长时间阻塞在 `while` 循环，放大资源占用。

## 技术原因 (❌)
1. `chats` 非 start 分支使用 `String response = userQueue.poll(); while (response == null) { ... } return response;` ——一次请求最多获取一个元素。
2. 队列中的 token 粒度过细（几乎一个字/一个 JSON），导致请求数量=token 数。
3. `while(response == null)` 直接阻塞 Tomcat 线程，模型结束后仍在空队列上死等。

```java
// ❌ 当前实现
String response = userQueue.poll();
while (response == null) {
    response = userQueue.poll();
    Thread.sleep(1);
}
return R.ok().message(response);
```

## 正确实现方案 (✅)
1. 去掉阻塞等待：若队列为空，立即返回 `""`，由前端控制轮询节奏。
2. 每次请求使用循环 `poll()` 将当前可用的全部内容拼接返回（直到遇到 `end` 或队列空）。
3. 或者直接改造成 SSE/StreamingResponseBody，让前端保持单条长连接消费流式输出。

```java
// ✅ 建议实现
StringBuilder builder = new StringBuilder();
String item;
boolean hitEnd = false;
while ((item = userQueue.poll()) != null) {
    if ("end".equals(item)) {
        hitEnd = true;
        break;
    }
    builder.append(item);
}
return hitEnd ? R.ok().message(builder.toString()).data("end", true)
              : R.ok().message(builder.toString());
```

## 测试验证
- **测试场景**：
  - 场景1：发送一条长文本，检查新实现是否一次返回多个 token。
  - 场景2：模型结束后继续轮询，确保不会长时间阻塞。
- **验证方法**：
  - 方法1：统计 Network 请求数量是否明显下降，总耗时是否接近模型真实耗时。
  - 方法2：查看线程堆栈，确认没有大量线程停在 `while(response == null)`。

## 预防措施
- 设计流式队列时，避免“单元素 = 单请求”的实现，应支持批量 drain。
- 在上线前对高频接口做全链路 profiling，确保请求数和耗时符合预期。
- 推广 SSE/HTTP2 流式方案，减少自建轮询协议的复杂度。

## 可复用经验
- 对流式场景，后端应直接提供流式接口或一次返回足够多的片段，避免 per-token HTTP。
- 队列消费策略要评估前端交互方式，单次仅返回一个元素会放大延迟。
- 阻塞等待一定要设置超时或改成非阻塞，否则容易造成线程耗尽。
