# 问题序号：PDF.js 卡顿转为 MuPDF.js 性能优化

## 问题元信息
- **问题分类**：`性能`
- **严重程度**：`高`
- **影响范围**：`PDF 阅读和笔记功能、所有使用 PDF 功能的用户`
- **发现日期**：`2025-01-13`
- **解决状态**：`已解决`

## 问题现象

使用 PDF.js 渲染 PDF 文档时出现严重的性能问题：

1. **渲染卡顿**：
   - PDF 页面渲染速度慢，特别是大文件或多页文档
   - 滚动时出现明显的卡顿和延迟
   - 缩放操作响应缓慢

2. **内存占用高**：
   - PDF.js 占用大量内存
   - 大文件加载时可能导致内存溢出
   - 长时间使用后内存持续增长

3. **渲染质量问题**：
   - 部分 PDF 图表可能缺失或模糊
   - 高 DPI 支持需要手动实现，代码复杂
   - 字体支持依赖 CMap 文件，配置复杂

4. **用户体验差**：
   - 页面加载时间长
   - 交互响应慢
   - 影响用户正常使用 PDF 阅读和笔记功能

## 复现步骤

1. 步骤1：打开包含多页或大文件的 PDF 文档
2. 步骤2：尝试滚动页面或进行缩放操作
3. 步骤3：观察页面渲染速度和交互响应
4. 步骤4：检查浏览器内存占用情况

**触发条件**：
- PDF 文件较大（>10MB）
- PDF 页数较多（>50页）
- 设备性能较低（移动设备或低配电脑）
- 浏览器版本较旧（Chrome 99）

## 用户体验

- **加载速度慢**：用户需要等待较长时间才能看到 PDF 内容
- **交互卡顿**：滚动、缩放等操作不流畅，影响使用体验
- **内存占用高**：可能导致浏览器崩溃或设备卡死
- **功能受限**：性能问题限制了 PDF 功能的正常使用

## 技术原因 (❌)

1. **PDF.js 性能限制**：
   - PDF.js 是纯 JavaScript 实现的 PDF 渲染库
   - JavaScript 执行速度相比原生代码较慢
   - 大文件或多页文档渲染时性能瓶颈明显

2. **内存管理问题**：
   - PDF.js 需要将整个 PDF 文档加载到内存
   - 渲染时创建大量临时对象
   - 内存回收不及时，导致内存占用持续增长

3. **渲染复杂度高**：
   - PDF.js 需要解析 PDF 格式并转换为 Canvas 绘制
   - 字体渲染依赖 CMap 文件，增加加载时间
   - 高 DPI 支持需要手动实现，代码复杂

4. **架构设计问题**：
   - PDF.js 使用 Worker 线程处理，但通信开销大
   - 渲染任务无法有效取消，导致资源浪费
   - 缺乏有效的缓存机制

## 正确实现方案 (✅)

1. **迁移到 MuPDF.js**：
   - MuPDF.js 基于 WebAssembly，性能接近原生代码
   - 渲染速度更快，内存占用更低
   - 支持完整的 PDF 特性，渲染质量更高

2. **创建适配层**：
   - 创建 `MuPDFAdapter.ts` 适配层，提供与 PDF.js 兼容的 API
   - 保持对外接口不变，内部实现替换
   - 降低迁移成本和风险

3. **优化渲染流程**：
   - 使用 MuPDF.js 的 `toPixmap` 方法生成像素图
   - 将 RGB 数据转换为 RGBA 数据后绘制到 Canvas
   - 简化高 DPI 处理逻辑

4. **资源管理优化**：
   - 及时清理渲染资源（pixmap、页面对象等）
   - 优化内存使用，避免内存泄漏

**MuPDF 适配层实现**：

```typescript:imates-web/src/services/pdf/adapters/MuPDFAdapter.ts
// ✅ MuPDF 适配层，提供与 PDF.js 兼容的 API
import * as mupdf from 'mupdf'

export class MuPDFDocumentProxy {
  private doc: mupdf.Document
  private _numPages: number

  constructor(doc: mupdf.Document) {
    this.doc = doc
    this._numPages = doc.countPages()
  }

  get numPages(): number {
    return this._numPages
  }

  async getPage(pageNum: number): Promise<MuPDFPageProxy> {
    const page = this.doc.loadPage(pageNum - 1)
    return new MuPDFPageProxy(page)
  }
}

export class MuPDFPageProxy {
  private page: mupdf.Page

  getViewport(params: { scale: number }) {
    const bounds = this.page.getBounds()
    const width = bounds[2] - bounds[0]
    const height = bounds[3] - bounds[1]

    return {
      width: width * params.scale,
      height: height * params.scale,
      scale: params.scale,
    }
  }

  render(renderContext: {
    canvasContext: CanvasRenderingContext2D
    viewport: { width: number; height: number; scale: number }
  }): { promise: Promise<void> } {
    const { canvasContext, viewport } = renderContext
    const bounds = this.page.getBounds()
    const pageWidth = bounds[2] - bounds[0]
    const pageHeight = bounds[3] - bounds[1]

    const scaleX = viewport.width / pageWidth
    const scaleY = viewport.height / pageHeight

    const matrix: mupdf.Matrix = [scaleX, 0, 0, scaleY, 0, 0]

    // 使用 MuPDF 渲染到 Pixmap
    const pixmap = this.page.toPixmap(
      matrix,
      mupdf.ColorSpace.DeviceRGB,
      false
    )

    // 将 RGB 转换为 RGBA
    const pixels = pixmap.getPixels()
    const width = pixmap.getWidth()
    const height = pixmap.getHeight()

    const rgbData = new Uint8Array(pixels)
    const rgbaData = new Uint8ClampedArray(width * height * 4)

    for (let i = 0; i < width * height; i++) {
      const rgbIndex = i * 3
      const rgbaIndex = i * 4
      rgbaData[rgbaIndex] = rgbData[rgbIndex]
      rgbaData[rgbaIndex + 1] = rgbData[rgbIndex + 1]
      rgbaData[rgbaIndex + 2] = rgbData[rgbIndex + 2]
      rgbaData[rgbaIndex + 3] = 255
    }

    // 绘制到 Canvas
    const imageData = new ImageData(rgbaData, width, height)
    canvasContext.putImageData(imageData, 0, 0)

    // 清理资源
    pixmap.destroy()

    return { promise: Promise.resolve() }
  }
}
```

## 预防措施

- **措施1**：性能监控和评估
  - 在引入新的渲染库前，进行性能基准测试
  - 建立性能监控机制，及时发现性能问题
  - 定期评估现有技术的性能表现

- **措施2**：技术选型考虑
  - 优先选择基于 WebAssembly 的高性能库
  - 考虑库的维护状态和社区支持
  - 评估迁移成本和风险

- **措施3**：适配层设计
  - 使用适配层模式，隔离底层实现
  - 保持对外接口稳定，便于后续替换
  - 提供清晰的 API 文档和类型定义

- **措施4**：资源管理
  - 及时清理不再使用的资源
  - 使用 WeakMap/WeakSet 避免内存泄漏
  - 监控内存使用情况，及时发现问题

- **措施5**：渐进式迁移
  - 使用 feature flag 控制新功能上线
  - 保留旧代码作为回退方案
  - 充分测试后再完全切换
