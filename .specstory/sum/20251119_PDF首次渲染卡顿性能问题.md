问题序号：PDF首次渲染卡顿性能问题

## 问题元信息
- **问题分类**：`性能`
- **严重程度**：`高`
- **影响范围**：`PDF 查看（PdfPage.vue）在 Android WebView 中的首次进入体验`
- **发现日期**：`2025-11-19`
- **解决状态**：`已解决`

## 问题现象
- 在 Android WebView 中打开 PDF 时，进入 PDF 页面首屏明显卡顿，白屏或迟迟不出现内容，耗时约 1s 以上。
- 同一份 PDF 在桌面浏览器中体验相对正常，说明问题与 WebView 性能和前端实现强相关。

## 复现步骤
1. 在 Android WebView 中加载 `webapp/index.html` 所承载的 Vue 应用。
2. 进入使用 `PdfPage.vue` 的 PDF 查看页面，加载一份多页教材 PDF。
3. 观察首次进入该 PDF 时页面响应：会出现明显卡顿，滚动和手势也在首屏阶段不顺畅。

## 用户体验
- 影响点1：首次进入 PDF 加载等待时间较长，用户误以为应用卡死。
- 影响点2：手势滚动、缩放在首屏阶段响应迟缓，打断阅读节奏。
- 影响点3：对拍照搜题、教材查看等以 PDF 为核心的场景整体观感较差。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`：PDF 渲染组件，包含加载、布局计算、Canvas 绘制等核心逻辑。
- **涉及模块**：
  - MuPDF WebAssembly 渲染模块（`mupdf-wasm.wasm` / `mupdf.js`）。
  - PDF 查看路由页面（包含 `PdfPage` 的上层视图，例如 `PdfViewerView.vue`）。

## 技术原因 (❌)
1. 原因1：`render` 函数中对所有页面使用 `await Promise.all(layouts.map(...))` 并行渲染，导致在单线程 JS 环境中一次性堆积了大量重 CPU 运算和内存开销。
2. 原因2：每一页渲染流程过重，包括：
   - 调用 `page.toPixmap(matrix, mupdf.ColorSpace.DeviceRGB, false, true)` 生成高分辨率 Pixmap；
   - 遍历 `width * height` 像素执行 RGB→RGBA 转换；
   - 使用 `ctx.putImageData(new ImageData(rgbaData, width, height), 0, 0)` 一次性写入大块像素到 Canvas。
3. 原因3：所有页面在首次进入时统一执行上述重渲染流程，缺乏首屏优先和分批调度策略，导致首次进入必须等待所有页面渲染结束，主线程长时间被占用。

❌ 错误代码示例（节选）：

```ts
// 旧实现：一次性 Promise.all 渲染所有页面
const baseDpr = window.devicePixelRatio || 1
const renderDpr = baseDpr * 2
const matrix: mupdf.Matrix = [renderScale * renderDpr, 0, 0, renderScale * renderDpr, 0, 0]

await Promise.all(
  layouts.map(async (layout, index) => {
    if (signal.aborted) return
    const canvas = pageCanvasRefs.value[index]
    if (!canvas) return

    const page = doc.loadPage(index)
    try {
      if (signal.aborted) return

      const bounds = page.getBounds()
      const renderWidth = (bounds[2] - bounds[0]) * renderScale
      const renderHeight = (bounds[3] - bounds[1]) * renderScale

      const ctx = canvas.getContext('2d')
      if (!ctx) return

      canvas.width = renderWidth * renderDpr
      canvas.height = renderHeight * renderDpr
      canvas.style.width = `${renderWidth}px`
      canvas.style.height = `${renderHeight}px`

      const pixmap = page.toPixmap(matrix, mupdf.ColorSpace.DeviceRGB, false, true)
      try {
        if (signal.aborted) return

        const pixels = pixmap.getPixels()
        const width = pixmap.getWidth()
        const height = pixmap.getHeight()
        const rgbData = new Uint8Array(pixels)
        const rgbaData = new Uint8ClampedArray(width * height * 4)

        for (let i = 0; i < width * height; i++) {
          rgbaData[i * 4] = rgbData[i * 3]
          rgbaData[i * 4 + 1] = rgbData[i * 3 + 1]
          rgbaData[i * 4 + 2] = rgbData[i * 3 + 2]
          rgbaData[i * 4 + 3] = 255
        }

        if (!signal.aborted) {
          ctx.putImageData(new ImageData(rgbaData, width, height), 0, 0)
        }
      } finally {
        pixmap.destroy()
      }
    } finally {
      page.destroy()
    }
  })
)
```

## 正确实现方案 (✅)
1. 方案1：将「第二阶段页面渲染」改为**按小批次循环渲染**，例如每批处理 2 页，批次间 `await nextTick()`，避免长时间阻塞主线程。
2. 方案2：在不改变视觉效果前提下，适当降低渲染 DPR（如从 `baseDpr * 2` 降为 `baseDpr * 1.5`），平衡清晰度和性能。
3. 方案3：通过 `console.time` 埋点细化到 `loadPdf`、布局计算（3.3.4）、单页渲染（3.3.5.1），精确定位瓶颈并持续调优渲染策略。

✅ 修正后代码示例（节选，按批次渲染）：

```ts
// 使用设备像素比，可以在清晰度和性能之间取得平衡
const baseDpr = window.devicePixelRatio || 1
// 结合设备能力与清晰度要求设定 DPR，例如 1.5
const renderDpr = baseDpr * 1.5
const matrix: mupdf.Matrix = [renderScale * renderDpr, 0, 0, renderScale * renderDpr, 0, 0]

console.time('3.3.5')
const batchSize = 2
for (let start = 0; start < layouts.length; start += batchSize) {
  if (signal.aborted) return

  const end = Math.min(start + batchSize, layouts.length)

  await Promise.all(
    layouts.slice(start, end).map(async (layout, offset) => {
      const index = start + offset
      console.time('3.3.5.1')
      if (signal.aborted) return

      const canvas = pageCanvasRefs.value[index]
      if (!canvas) return

      const page = doc.loadPage(index)
      try {
        if (signal.aborted) return

        const bounds = page.getBounds()
        const renderWidth = (bounds[2] - bounds[0]) * renderScale
        const renderHeight = (bounds[3] - bounds[1]) * renderScale

        const ctx = canvas.getContext('2d')
        if (!ctx) return

        canvas.width = renderWidth * renderDpr
        canvas.height = renderHeight * renderDpr
        canvas.style.width = `${renderWidth}px`
        canvas.style.height = `${renderHeight}px`

        const pixmap = page.toPixmap(matrix, mupdf.ColorSpace.DeviceRGB, false, true)
        try {
          if (signal.aborted) return

          const pixels = pixmap.getPixels()
          const width = pixmap.getWidth()
          const height = pixmap.getHeight()
          const rgbData = new Uint8Array(pixels)
          const rgbaData = new Uint8ClampedArray(width * height * 4)

          for (let i = 0; i < width * height; i++) {
            rgbaData[i * 4] = rgbData[i * 3]
            rgbaData[i * 4 + 1] = rgbData[i * 3 + 1]
            rgbaData[i * 4 + 2] = rgbData[i * 3 + 2]
            rgbaData[i * 4 + 3] = 255
          }

          if (!signal.aborted) {
            ctx.putImageData(new ImageData(rgbaData, width, height), 0, 0)
          }
        } finally {
          pixmap.destroy()
        }
      } finally {
        page.destroy()
      }
      console.timeEnd('3.3.5.1')
    })
  )

  // 每批渲染完后让出一次主线程，避免长时间卡死
  await nextTick()
}
console.timeEnd('3.3.5')
```

## 测试验证
- **测试场景**：
  - 场景1：在 Android WebView 上打开多页 PDF，观察首屏出现时间及渲染过程中是否可以滚动。
  - 场景2：在不同页数（10、50、100 页）PDF 上对比优化前后 `3.3.5` 和 `3.3.5.1` 的耗时。
- **验证方法**：
  - 方法1：通过 DevTools / WebView 日志查看 `console.time` 输出，确认渲染时间被拆分为多批且首批耗时明显下降。
  - 方法2：主观体验：首次进入时能快速看到前几页内容，并能平滑滚动，不再出现长时间白屏或完全卡死。

## 预防措施
- 措施1：对于涉及大数据量或高计算量的渲染逻辑，默认采用“分批 + 首屏优先”策略，不直接对全量数据做 Promise.all。
- 措施2：在引入第三方重计算库（如 MuPDF、Math 排版等）时，配套加入 `console.time` 埋点，首版就评估性能。
- 措施3：在 WebView / 低端设备场景下优先做性能压测，避免桌面 Chrome 正常而移动端严重卡顿的情况。

## 可复用经验
- 经验1：在 JS 单线程环境中，大量 CPU 密集任务不要用 Promise.all 全量并发，而要拆批次、让出事件循环。
- 经验2：复杂渲染（PDF、富文本、数学公式）必须在首版就加入性能埋点，方便快速定位瓶颈。
- 经验3：首屏时间比“全部渲染完成时间”更重要，优先保障用户可见区域的渲染与可交互性。
