问题序号：PDF手写高亮多条绘制卡顿问题

## 问题元信息
- **问题分类**：前端
- **严重程度**：中
- **影响范围**：Web 端 PDF 阅读器中手写高亮功能（多条高亮笔记绘制场景）
- **发现日期**：2025-11-17
- **解决状态**：已解决

## 问题现象
在 Web 端 PDF 阅读器中使用手写高亮功能时：
- 单条高亮笔记绘制基本流畅。
- 当用户在同一页或多页上**快速连续绘制多条手写高亮线条**时：
  - 每次抬笔后界面会出现明显短暂卡顿或掉帧。
  - 卡顿程度随 PDF 页数增加、高分辨率渲染配置（高 DPR）而加重。

## 复现步骤
1. 打开 Web 端 PDF 阅读页面，加载一份页数较多或页面较大的 PDF。
2. 切换到“手写高亮”模式。
3. 在某一页上快速绘制多条高亮线条：按下 → 移动 → 抬笔，连续重复多次。
4. 观察：
   - 每完成一条线（抬笔）后，界面有明显的停顿。
   - 连续多条线后，整体交互感觉“变重”，预览偶尔不跟手。

## 用户体验
- 影响点1：用户快速圈画多个重点时，每画完一笔都要等待界面“缓一缓”，打断操作节奏。
- 影响点2：在复杂 PDF（多页、高分辨率）上使用手写高亮时，卡顿感明显，用户容易误以为程序卡死或性能很差。
- 影响点3：在教学或批改作业等需要频繁手写高亮的场景中，效率和流畅度明显下降。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/components/PdfPage.vue`
- **涉及模块**：
  - PDF 手写高亮模块（PointerDown/Move/Up + Ink 注释创建）
  - PDF 渲染模块（`render()` 全量渲染逻辑）

## 技术原因 (❌)
1. **每次手写结束都触发整份 PDF 全量重渲**：
   - 在手写高亮的 `PointerUp` 逻辑中，完成一条笔画后会：
     - 创建 MuPDF Ink 注释：`page.createAnnotation('Ink') + setInkList + page.update()`。
     - 然后调用 `await render()`：
       ```ts
       // PdfPage.vue 旧逻辑（简化）
       const handleHighlightPointerUp = async (...) => {
         // ... 创建 Ink 注释
         page.update()

         // ❌ 每次结束一条笔画都重渲整份 PDF
         await render()
       }
       ```
   - `render()` 会：
     - 遍历 `doc.countPages()` 的所有页。
     - 计算每页布局尺寸，更新 `pageLayouts`。
     - 使用高 DPR（`renderDpr = baseDpr * 2`）渲染每一页为 pixmap，再绘制到每个 `pageCanvas`。
   - 当用户连续绘制多条线时，每条线的 `PointerUp` 都会触发一次完整的 PDF 重渲，累积耗时导致明显卡顿。

2. **高 DPR + 多页渲染增加单次 `render()` 成本**：
   - `render()` 中使用：
     ```ts
     const baseDpr = window.devicePixelRatio || 1
     const renderDpr = baseDpr * 2
     const matrix: mupdf.Matrix = [renderScale * renderDpr, 0, 0, renderScale * renderDpr, 0, 0]
     ```
   - 这意味着每页的渲染分辨率非常高，像素数量约为普通 DPR 的 4 倍。
   - 在多页 PDF（几十页）场景下，全量渲染成本极高。

3. **初期实现中，实时预览、坐标转换、日志也叠加了一定负载**（已通过重构缓解）：
   - PointerMove 阶段曾经：
     - 每次都进行 Screen → Normalized → PDF → Screen 的完整坐标链路；
     - 在坐标转换和预览绘制中输出大量详细 `console.log`；
   - 这些在高频 PointerMove 路径上会进一步放大卡顿问题。

## 正确实现方案 (✅)
1. **保留全量 `render()` 作为“初次加载/切换 PDF”使用，新增单页渲染函数 `renderPage(pageIndex)`**：
   - 从现有 `render()` 中抽出单页渲染逻辑，封装为 `renderPage`：
     ```ts
     const renderPage = async (pageIndex: number) => {
       if (!pdfDoc.value || isUnmounting) return
       const doc = pdfDoc.value

       // 保证页面布局和 canvas 已经就位
       const layout = pageLayouts.value[pageIndex]
       const canvas = pageCanvasRefs.value[pageIndex]
       if (!layout || !canvas) return

       const renderScale = 1.0
       const baseDpr = window.devicePixelRatio || 1
       const renderDpr = baseDpr * 2
       const matrix: mupdf.Matrix = [renderScale * renderDpr, 0, 0, renderScale * renderDpr, 0, 0]

       const page = doc.loadPage(pageIndex)
       try {
         const bounds = page.getBounds()
         const renderWidth = (bounds[2] - bounds[0]) * renderScale
         const renderHeight = (bounds[3] - bounds[1]) * renderScale

         const ctx = canvas.getContext('2d')
         if (!ctx) return

         canvas.width = renderWidth * renderDpr
         canvas.height = renderHeight * renderDpr
         canvas.style.width = `${renderWidth}px`
         canvas.style.height = `${renderHeight}px`

         const pixmap = page.toPixmap(matrix, mupdf.ColorSpace.DeviceRGB, false, true)
         try {
           const pixels = pixmap.getPixels()
           const width = pixmap.getWidth()
           const height = pixmap.getHeight()
           const rgbData = new Uint8Array(pixels)
           const rgbaData = new Uint8ClampedArray(width * height * 4)

           for (let i = 0; i < width * height; i++) {
             rgbaData[i * 4] = rgbData[i * 3]
             rgbaData[i * 4 + 1] = rgbData[i * 3 + 1]
             rgbaData[i * 4 + 2] = rgbData[i * 3 + 2]
             rgbaData[i * 4 + 3] = 255
           }

           ctx.putImageData(new ImageData(rgbaData, width, height), 0, 0)
         } finally {
           pixmap.destroy()
         }
       } finally {
         page.destroy()
       }
     }
     ```

2. **在手写高亮 PointerUp 中，只重渲当前页，而不是整份 PDF**：
   ```ts
   const handleHighlightPointerUp = async (event, pageIndex, layout) => {
     // ... 省略模式检查、补尾点、清除预览

     if (!stroke || stroke.points.length < 2) {
       console.log('[手写高亮] PointerUp 笔画点数不足，忽略', {
         pageIndex,
         pointsCount: stroke?.points.length ?? 0,
       })
       return
     }

     try {
       const pdf = pdfDoc.value.asPDF()
       if (!pdf) return

       const page = pdf.loadPage(pageIndex) as mupdf.PDFPage
       const annot = page.createAnnotation('Ink')

       const inkList = [stroke.points.map((p: HighlightStrokePoint) => [p.x, p.y] as mupdf.Point)]
       ;(annot as any).setInkList?.(inkList)
       ;(annot as any).setColor?.([1, 1, 0])

       const bounds = page.getBounds()
       const pageHeight = bounds[3] - bounds[1]
       const width = Math.max(pageHeight * 0.003, 1)
       ;(annot as any).setBorderWidth?.(width)

       page.update()

       console.log('[手写高亮] PointerUp 已创建 Ink 注释，开始重渲当前页', {
         pageIndex,
         pointsCount: stroke.points.length,
       })

       // ✅ 只重渲当前页
       await renderPage(pageIndex)
     } catch (e) {
       console.error('创建高亮注释失败', e)
     }
   }
   ```

3. **对坐标转换和预览部分做性能优化**（已实施）：
   - 抽象 Screen ↔ Normalized ↔ PDF ↔ Screen 的转换函数，并在其中使用 `pageBoundsCache` 缓存每页 bounds，避免重复 `loadPage/getBounds`：
     ```ts
     const pageBoundsCache = ref<Map<number, [number, number, number, number]>>(new Map())

     const normalizedToPdfPoint = (norm, pageIndex) => {
       if (!pdfDoc.value) return null

       const cached = pageBoundsCache.value.get(pageIndex)
       let bounds: [number, number, number, number]

       if (cached) {
         bounds = cached
       } else {
         const pdf = pdfDoc.value.asPDF()
         if (!pdf) return null
         const page = pdf.loadPage(pageIndex) as mupdf.PDFPage
         bounds = page.getBounds() as [number, number, number, number]
         page.destroy()
         pageBoundsCache.value.set(pageIndex, bounds)
       }
       // ... 使用 bounds 计算 pdfPoint
     }
     ```
   - 删除 PointerMove 高频路径上大量详细 `console.log`，只保留关键节点的短日志（PointerDown/Move/Up、drawStrokePreview）。

## 关键代码/公式
- **单页渲染函数**：`renderPage(pageIndex)`（见上方代码示例）。
- **PointerUp 调用优化**：
  ```ts
  // 旧实现（✗）：
  await render() // 整份 PDF 重渲

  // 新实现（✓）：
  await renderPage(pageIndex) // 仅当前页重渲
  ```

- **坐标转换缓存公式**：
  ```ts
  // bounds = [x0, y0, x1, y1]
  pageWidth = x1 - x0
  pageHeight = y1 - y0

  // PDF 坐标 -> 屏幕坐标
  nx = (pdfX - x0) / pageWidth
  ny = (pdfY - y0) / pageHeight
  screenX = nx * layout.width * scale
  screenY = ny * layout.height * scale
  ```

## 测试验证
- **测试场景**：
  - 场景1：单条长线绘制
    - 步骤：在单页 PDF 上画一条长线，观察 PointerMove 流畅度和 PointerUp 停顿时间。
    - 预期：PointerMove 流畅，PointerUp 有短暂但可接受的单页重渲时间。
  - 场景2：多条短线快速绘制
    - 步骤：在多页 PDF 的同一页上快速连续画多条短线。
    - 预期：每条线结束时的停顿明显短于旧实现（不再感受到“整本重画”的卡顿）。
  - 场景3：跨页绘制
    - 步骤：在不同页分别画高亮线，观察各页是否正确显示 Ink 注释且渲染时间合理。

- **验证方法**：
  - 方法1：通过浏览器 Performance 工具对比 PointerUp 触发时的帧时间，确认单页渲染耗时明显低于整本渲染。
  - 方法2：通过控制台日志观察
    ```
    [手写高亮] PointerUp 已创建 Ink 注释，开始重渲当前页 { pageIndex, pointsCount }
    ```
    确认 PointerUp 只触发了单页渲染逻辑。

## 预防措施
- 措施1：对于所有“局部更新”的交互（如单页注释、单页删除），优先考虑设计“单页渲染函数”，避免默认调用全量渲染。
- 措施2：在引入新功能（如更多类型的注释）时，明确区分“预览层更新”和“PDF 位图更新”，防止所有更新都落到`render()`上。
- 措施3：对高频操作路径（PointerMove/PointerUp）保持 Profiling 意识，避免在这些路径中加入重度逻辑（如全量重渲或大量日志）。

## 可复用经验
- 经验1：在 PDF/画布类应用中，**全量渲染只适合初始化/大变更**，日常交互必须靠“增量渲染”来保持性能。
- 经验2：将渲染逻辑拆成“全量渲染函数 + 单页/局部渲染函数”是一种通用模式，适用于 PDF、图片编辑器、地图等场景。
- 经验3：在引入实时预览和注释功能时，务必将“预览（前端层）”和“持久化（PDF/服务端层）”分层设计，预览尽量轻量、频繁，持久化尽量批量、按需触发。
