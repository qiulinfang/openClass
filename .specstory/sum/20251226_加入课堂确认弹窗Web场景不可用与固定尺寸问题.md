问题序号：加入课堂确认弹窗Web场景不可用与固定尺寸问题

## 问题元信息
- **问题分类**：`前端`
- **严重程度**：`中`
- **影响范围**：`我的-加入课堂弹窗、Web 演示环境`
- **发现日期**：`2025-12-26`
- **解决状态**：`已解决`

## 问题现象
1. 在 Web 场景（无 AndroidBridge）打开“加入课堂”弹窗，无法加载教室列表，提示环境不支持，导致无法演示/测试 UI。
2. 弹窗宽高使用固定 `initialWidth/initialHeight/minWidth/minHeight`，视觉上不随内容变化；用户要求“调整为内容高度宽度”。
3. 选择器布局需要按用户要求调整（`selector-grid` 改为纵向，`selector-column` 用 flex 布局并有间隔），并删除不需要的 UI 区块。

## 复现步骤
1. 在非 Android WebView 环境打开 imates-web。
2. 进入“我的/工具箱”打开加入课堂弹窗。
3. 观察：教室下拉不可用/报错；弹窗尺寸固定；布局不符合预期。

## 用户体验
- Web 环境无法演示加入课堂选择流程。
- 弹窗固定尺寸导致空白或拥挤，观感差。
- 选择器布局不符合交互预期。

## 相关文件/模块
- **涉及文件**：
  - `imates-web/src/views/MyProfileView.vue`：加入课堂弹窗、教室树加载、选择器布局样式。
  - `imates-web/src/components/DraggableDialog.vue`：弹窗尺寸控制（新增 `autoSize`）。
  - `imates-web/src/services/business/android-bridge.ts`：原生教室树/课堂/投屏接口。
- **涉及模块**：
  - 加入课堂流程：教室树加载、确认加入/退出。
  - 通用弹窗：拖拽弹窗尺寸策略。

## 技术原因 (❌)
1. 教室树数据依赖 `AndroidBridge.fetchClassroomTree()`，Web 环境不可用导致 UI 无法选择。
2. 弹窗组件仅支持固定像素宽高（`initialWidth/initialHeight`），未提供“内容自适应”能力。

错误示例：
```vue
<!-- ❌ MyProfileView.vue：固定尺寸 + Web 环境直接报错 -->
<DraggableDialog
  :initial-width="420"
  :initial-height="280"
  :min-width="300"
  :min-height="220"
/>
```

## 正确实现方案 (✅)
1. Web 环境提供 mock 数据：当 `androidBridge.isAndroidBridgeAvailable()` 为 false，注入模拟 `classroomTree`，保证下拉可选。
2. 弹窗支持自适应：在 `DraggableDialog` 增加 `autoSize`，并在使用方设置 `:auto-size="true"`，移除固定宽高参数。
3. 按需求调整布局：
   - `.selector-grid` 使用 `flex-direction: column`
   - `.selector-column` 使用 `flex row + gap`，label 固定宽度，`CommonSelect` `flex:1`
4. 删除不需要的 UI 块（如 selection-summary / header 区域）。

正确示例：
```vue
<!-- ✅ MyProfileView.vue：自适应尺寸 -->
<DraggableDialog
  :auto-size="true"
  :confirm-disabled="!canConfirmJoinClass"
/>
```

```ts
// ✅ MyProfileView.vue：Web mock（示意）
if (!androidBridge.isAndroidBridgeAvailable()) {
  classroomTree.value = {
    cities: ['北京', '上海'],
    schoolsMap: { 北京: ['第一中学'], 上海: ['实验中学'] },
    classroomsMap: { 北京: { 第一中学: [{ id: 'BJ-1', name: '高一(1)班' }] } },
  }
}
```

```ts
// ✅ DraggableDialog.vue：autoSize（示意）
if (props.autoSize) {
  return { width: 'auto', height: 'auto' }
}
```

## 测试验证
- **测试场景**：
  - 场景1：Web 环境打开弹窗，城市/学校/教室下拉可选。
  - 场景2：Android WebView 环境仍走原生 `fetchClassroomTree`。
  - 场景3：退出课堂/加入课堂按钮禁用态正确（未选完不可确认）。
  - 场景4：弹窗尺寸随内容变化，不出现固定空白。
- **验证方法**：
  - 方法1：实际点击选择下拉，观察 confirm 按钮启用/禁用。
  - 方法2：对比 Android 与 Web 两种环境行为。

## 预防措施
- 对“依赖原生能力”的功能增加 Web fallback（mock 或降级提示），保证开发/测试可用。
- 通用组件（Dialog）提供明确的尺寸策略：固定/自适应/全屏。

## 可复用经验
- WebView 项目建议始终提供一套“无原生能力的演示模式”，避免研发阶段被原生依赖阻塞。
- 组件能力（如 autoSize）应下沉到通用组件，避免业务组件重复 hack。
