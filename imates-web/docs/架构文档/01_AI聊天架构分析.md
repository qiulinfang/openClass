# AI 聊天系统架构分析

## 1. 概述

AI 聊天是研伴学生端的核心交互引擎，承载了"通用问答"、"习题导疑"、"作业辅导"、"教材解析"四大业务场景。系统在 Android WebView 的受限环境下，通过精巧的分层架构与多种设计模式，实现了高内聚低耦合的工程结构。

---

## 2. 分层架构

系统严格遵循四层架构，自底向上依次为：

```
┌─────────────────────────────────────────────┐
│  表现层 (Presentation)                       │
│  MainChatPanel / ChatBubble / MessageRenderer│
├─────────────────────────────────────────────┤
│  状态管理层 (State)                          │
│  aiGeneralStore / aiExerciseStore / ...      │
├─────────────────────────────────────────────┤
│  业务逻辑层 (Business Logic)                  │
│  useChatEngine / useChatPersistence / ...    │
├─────────────────────────────────────────────┤
│  基础设施层 (Infrastructure)                  │
│  AiChatApi / HttpClient / AndroidBridge      │
└─────────────────────────────────────────────┘
```

### 2.1 基础设施层

负责底层通信与平台适配，对上层完全透明。

| 组件 | 职责 |
|------|------|
| `AiChatApi` | 封装轮询流式通信协议，管理请求生命周期 |
| `HttpClient` | 统一 HTTP 请求拦截、超时、重试 |
| `AndroidBridge` | 桥接原生拍照、截图、日志等能力 |
| `chatStorage` | IndexedDB 离线消息持久化 |

### 2.2 业务逻辑层

以 Composables 形式提取可复用逻辑，供各 Store 按需组合。

| Composable | 职责 |
|------------|------|
| `useChatEngine` | 消息发送核心引擎：流式回调、历史同步、状态机 |
| `useChatPersistence` | 会话与消息的本地持久化读写 |
| `useChatRetry` | 失败消息的重试与回滚逻辑 |
| `useChatSessions` | 多会话的创建、切换、删除管理 |
| `useMessageRenderer` | Markdown / LaTeX / HTML 富文本渲染 |
| `useHtmlMessageRawMap` | HTML 预览消息的原始内容映射 |

### 2.3 状态管理层

按业务场景垂直拆分为四个独立 Store，各自维护独立的会话与消息状态：

| Store | 场景 | 会话粒度 |
|-------|------|----------|
| `aiGeneralChatStore` | 悬浮球通用对话 | 按会话 |
| `aiExerciseChatStore` | 习题导疑 | 按题目 |
| `aiHomeworkChatStore` | 作业辅导 | 按作业 |
| `aiTextbookChatStore` | 教材解析 | 按章节 |

每个 Store 内部结构高度一致：
- `messages: Ref<ChatBubble[]>` — 消息列表
- `sessions` — 会话列表
- `currentSession` — 当前激活会话
- `isChatLoading` — 加载状态
- `sendMessage()` — 发送入口
- `loadHistory()` — 历史恢复

### 2.4 表现层

| 组件 | 职责 |
|------|------|
| `MainChatPanel.vue` | 侧边弹出式通用聊天面板 |
| `GlobalChatDialog.vue` | 全屏对话框模式 |
| `ChatBubble.vue` | 消息气泡：区分用户/AI、公式预览、代码高亮 |

## 3. 设计模式分析

### 3.1 策略模式 — 请求构建与校验 (Strategy Pattern)

AI 聊天系统针对不同的业务场景（通用、习题、作业、教材），通过**策略模式**实现了请求构建逻辑的解耦。这种模式使得系统能够根据当前上下文，动态选择不同的参数封装策略和接口地址。

#### 3.1.1 请求构建策略 (Build Strategies)
系统为每个 Store 定义了专属的构建函数，充当具体的策略实现：

*   **`buildAiGeneralMessage` (通用策略)**:
    *   **适用场景**: 悬浮球自由对话。
    *   **核心特征**: `bmNo` 指向 `sessionId`，`subject` 为空，支持 `isWebSearch` 开关。
*   **`buildAiExerciseMessage` (习题策略)**:
    *   **适用场景**: 习题列表/错题本导疑。
    *   **核心特征**: 注入真实的 `bmNo` (题号)，根据题目学科自动映射 `subject` (MATH/BIOLOGY)，并强制包含 `question` 和 `answer` 文本。
*   **`buildAiTextbookMessage` (教材策略)**:
    *   **适用场景**: 教材内容解析。
    *   **核心特征**: 通常指向 `previewPictureQA` 接口，支持截图输入。

#### 3.1.2 校验策略 (Validation Strategies)
除了构建请求，系统还匹配了对应的**校验策略**（位于 `src/stores/utils/requestValidator.ts`），确保不同场景下的参数合规性：

| 策略名称 | 校验重点 |
| :--- | :--- |
| **通用校验** | `sessionId`, `newValue`, `coversation`, `name`, `dstUrl` 等 8 个基础字段。 |
| **习题校验** | 强制要求 `bmNo` 为纯数字或 UUID，且 `subject` 必须是有效的学科代码。 |
| **截图校验** | 若 `dstUrl` 匹配截图接口，则强制检查 `imageList` 是否包含有效的 Base64 数据。 |

#### 3.1.3 策略切换示例
```typescript
// 以 aiExerciseChatStore 为例
const request = buildAiExerciseMessage(content, currentQuestion, ...); // 应用构建策略
validateExerciseChatRequest(request, currentQuestion.title);           // 应用校验策略
apiService.sendChatMessage(request, ...);                              // 统一执行
```

通过这种设计，`AiChatApi` 只需要处理统一的 `AiChatMessageRequest` 对象，而不需要感知复杂的业务规则，实现了极佳的扩展性。

### 3.2 模板/钩子模式 — 消息生命周期

`useChatEngine` 定义了消息处理的标准化生命周期，通过 `createSendChatCallbacks` 暴露三个钩子：

```
createSendChatCallbacks(tempReplyId, tempReply)
  → { onComplete, onStream, onHistoryUpdate }
```

- **`onStream(chunk, isComplete)`**：逐片段累积内容，驱动打字机效果
- **`onComplete(finalResponse)`**：消息终结，写入最终内容与 messageId
- **`onHistoryUpdate(history, agentStatus)`**：后端历史同步，签名去重

各 Store 只需调用此工厂方法即可获得完整的行为闭环，无需重复实现流式处理逻辑。

### 3.3 观察者模式 — 响应式数据驱动

Vue 3 的响应式系统 + Pinia 构成了天然的观察者链路：

```
AiChatApi (轮询) → store.messages[i].content = newValue
                                  ↓
                        ChatBubble.vue (自动重渲染)
```

通信层无需感知 UI 存在，只需修改 Store 中的响应式数据，表现层自动响应变化。这种解耦使得流式渲染的实现极为简洁。

### 3.4 桥接模式 — 平台能力抽象

`AndroidBridge` 将 Web 业务逻辑与 Android 原生实现彻底分离：

```
Web 层调用                         原生层实现
─────────────────────────────────────────────
bridge.takeScreenshot()    →    WebAppInterface.captureScreen()
bridge.openCamera()        →    WebAppInterface.launchCamera()
bridge.logToNative()       →    Logcat 输出
```

在浏览器开发环境下，`AndroidBridge` 提供完整的 Mock 实现，确保 Web 端可脱离原生独立运行调试。

### 3.5 适配器模式 — 数据格式转换

后端返回的 `BackendHistoryMessage` 与前端 UI 使用的 `ChatBubble` 结构不同。`historySyncUtils` 充当适配器：

```
BackendHistoryMessage          ChatBubble
─────────────────────    →    ─────────────
{ msgContent, msgType,         { content, messageType,
  senderType, createTime }       sender, timestamp }
```

核心适配逻辑：
- `alignTailMessageIdsFromHistory()` — 将后端消息 ID 对齐到前端气泡
- `buildHistorySignature()` — 生成历史指纹，避免重复同步

### 3.6 组合模式 — Composables 混入

Store 不通过继承，而是通过**组合多个 Composable** 获得能力：

```typescript
// aiGeneralChatStore 内部
const { createSendChatCallbacks } = useChatEngine({ messagesRef: messages, ... })
const { saveSession, loadSession } = useChatPersistence()
const { retryMessage }            = useChatRetry()
const { sessions, switchSession } = useChatSessions()
```

这种"组合优于继承"的方式比传统的 Mixin 或基类继承更灵活，每个 Store 可按需选取所需能力。

### 3.7 单例模式 — 全局服务

`AiChatApi` 和 `AndroidBridge` 采用单例模式，确保全局唯一实例：

```typescript
AndroidBridge.getInstance()  // 全局唯一桥接实例
```

避免重复创建 WebSocket 连接、原生接口注册等昂贵资源。

## 4. 核心流程：轮询流式机制

由于 WebView 对 SSE 支持有限，系统采用**状态机驱动的 HTTP 轮询**模拟流式效果：

```
用户发送消息
    │
    ▼
POST /ai/2.0/chat  (reason: "start")
    │
    ▼
后端返回首帧 { success: true, message: "..." }
    │
    ▼
前端解析 SSE 格式 (data: {...})
    │
    ├── 有 content → onStream(chunk) → 累积到 messages[i].content
    │
    ├── agent_status = "drawing" → 控制帧，继续轮询
    │
    ├── message = "end" → onComplete() → 停止轮询
    │
    └── 空帧 → 继续轮询 (reason: "continue", 间隔 500ms)
```

关键设计决策：
- **无状态轮询**：每次请求独立，通过 `sessionId` 关联上下文
- **签名去重**：`buildHistorySignature` 防止历史消息重复同步
- **超时保护**：单次请求 60s 超时，防止轮询死循环

---

## 5. 架构总结

| 维度 | 设计选择 | 收益 |
|------|----------|------|
| 分层 | 四层架构（基础设施→业务逻辑→状态→表现） | 每层可独立测试、替换 |
| 场景隔离 | 四个独立 Store | 不同业务场景互不干扰 |
| 逻辑复用 | Composables 组合 | 避免继承链，灵活按需装配 |
| 平台适配 | Bridge 模式 | Web 端可脱离原生独立开发 |
| 流式通信 | 轮询 + 状态机 | 在受限 WebView 中实现流畅体验 |
| 数据一致性 | 适配器 + 签名去重 | 前后端消息精确对齐 |

这套架构使得系统在保持高性能的同时，具备了良好的可扩展性——新增一个 AI 对话场景只需新建一个 Store 并组合已有 Composables，无需修改核心引擎代码。
